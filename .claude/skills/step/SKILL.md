---
name: step
description: Run one implementation step of a work package under the step contract. The main session explains the step to the owner, delegates the build to the implementer agent, presents its report and asks one check question. Use for every implementation step after the decision is recorded, without the owner asking.
user-invocable: true
arguments: [wp, step]
allowed-tools: Read, Glob, Grep, Agent, Bash(git status*), Bash(git log*), Bash(git diff*), Bash(git show*), Bash(pnpm verify*)
---
Step $step of WP-$wp. The main session teaches and checks; the `implementer` agent builds.

1. **Gate.** `docs/learning/wp-$wp.md` says `decision: recorded` (or the step is `fast_path: known`) and the branch is `wp/$wp-*`. If not, the next action is `/learn-step $wp`.
2. **Explain before building, then stop.** In the chat, in plain words: what the step builds and which pattern it is, with a small example from this project (a real payload or SQL); how it compares with what the owner already knows (an earlier WP, their work stack); the alternatives, why not here and when each would win; the files; the explainer heading it implements (a decision `D<n>`, an open question `Q<n>` or an implementation choice); the ADR lines it touches. If the step was seen in an earlier WP, name it and say what is different. Check the step against the whole explainer first: if the code would differ from an ADR or a recorded decision, or two parts of the explainer disagree about it, stop and ask (`/adr` first for an ADR change). Then end the turn and wait for the owner's go, questions or objections. Never launch the implementer in the same turn as the explanation, even when the prompt that started the session already describes the step: a resume prompt says where to pick up, it is not a go. When the owner answers differently from your recommendation, challenge it with reasons (`AGENTS.md` section 5). A step marked `known` (fast path) may go straight on.
3. **Delegate.** Launch the `implementer` agent in the foreground (it works on this branch, so nothing else may touch git meanwhile) and do not end the turn before its report arrives: an ended turn leaves its half-written files to stop hooks that ask for a commit. If the tool still returns early, answer such a hook in one line (the implementer's work in progress, it commits at the end) and wait. Give it: WP and step, the title, the files, the explainer heading, the ADR lines, and anything the owner said about this step.
4. **Check the report** before presenting it: re-run `pnpm verify` on the branch, and look at `git show --stat HEAD` to confirm the commit matches the files claimed. If the implementer stopped with an open question, explain the question to the owner (problem, options, your recommendation after their answer) instead of continuing.
5. **Present** in the step contract's order: the demo output (short), the privacy check, the two step-log lines, the commit.
6. **One check question** on the mechanism just built, aimed at the likely misconception, usually "what happens when ..." on a failure or a change. The owner delegates the code and learns flows, patterns and design, so ask it in those terms, never "which test, file or line": first explain in plain words every part the question names (what it does, not only its code name), then check it against this test: someone who never opened the repo, having read only that explanation, can answer it. Then wait. A wrong or partial answer is challenged on the spot per `AGENTS.md` section 5: what is right in it (a part the owner got right is never listed as missing), the real behavior (the test or code line that proves it), why it was designed that way, the pattern name; note it in the step log. When the answer exposes a real gap in the code, propose the fix as the next small step. A wrong or partial answer, or a topic the owner found interesting or that is worth deeper study, also gets one line in `docs/learning/study-backlog.md` under its theme (see that file).
7. **Close and compact.** Follow-ups the owner raises after the check question (a rename, a rule, a question about the process) are explained with a recommendation, done on the owner's yes (process changes in their own `chore/` PR from `main`) and logged as one `Step M follow-ups` line in the step log. When the check question is answered and logged, the follow-ups are done and the branch is pushed, print a ready-to-copy line for the owner: `/compact WP-N on wp/N-<slug>. Step M done (<commit>). Next: step M+1 (<title>). Decision: <one-line summary, see Decision in docs/learning/wp-N.md>. Owner pending: <Docker commands or none>. Open items: see Step log.` Resuming relies on the explainer, the step log and `git log`, never on the conversation.

Rule: a step that creates or changes a process (an app, a worker, a consumer, a `dev` script, compose) ends with a real `pnpm dev` run showing the process up. In a local session with Docker, run the demo yourself (`pnpm test:int`, `pnpm dev` and a request) and show the output; in a cloud session without Docker, give the owner the exact commands and wait for their output before the next step.

For a WP of size M or larger, after about half the steps, run the `reviewer` agent on the branch diff before the next step.
