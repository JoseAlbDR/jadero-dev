---
name: wrap-wp
description: The closing checklist of a work package, from the last step to the merge and the start prompt of the next WP. Use when the last implementation step of a WP is committed, without the owner asking.
user-invocable: true
arguments: [wp]
allowed-tools: Read, Glob, Grep, Agent, Bash(git *), Bash(gh pr *), Bash(gh issue *), Bash(pnpm *), mcp__github__create_pull_request, mcp__github__pull_request_read, mcp__github__list_pull_requests, mcp__github__issue_read
---
Close WP-$wp. Go through the list in order, mark each item done or n/a with the reason, and stop where the owner is needed.

1. **Steps logged.** Every step in the explainer's Proposed steps is done and has its two step-log lines; `git log origin/main..HEAD` matches them.
2. **Map.** `/map` (the `cartographer` agent): code map JSON in sync, rendered clean, event catalog and flow updated for new events.
3. **Docs.** `AGENTS.md` status line and section 3 commands, the touched apps' `AGENTS.md`, `docs/sessions.md` or the process pages when the flow changed. Delegate to the `implementer` agent (as a docs step) when the edits are more than a few lines.
4. **Artifacts.** Every artifact in `docs/artifacts.md` whose source changed is republished and its row updated (the cartographer does it; check the rows).
5. **PR.** Title a conventional commit scoped to the service, body per `.github/PULL_REQUEST_TEMPLATE.md` with `Closes #<issue>`. Check first that no merged PR already holds this branch.
6. **Review.** The `reviewer` agent on the PR. Fix its findings (through the `implementer` agent, one commit per fix), push, re-run `pnpm verify` yourself.
7. **Docker demo.** The WP's processes running together (`pnpm dev:up`, `pnpm dev`, the main trace once, `pnpm test:int`). In a cloud session, give the owner the commands and wait for their output.
8. **Explain-back** in interview form, in the main session: why this way, what else, when to change it, what happens when it fails, the main trace drawn from memory. Each question comes in two halves: here (the mechanism in this project, short), then transfer (the same pattern in another domain, such as an online shop, payments or bookings, told as a concrete case with no project names). Each half is self-contained: a refresher, the facts needed and hints, never the answer, so the owner answers without scrolling back or opening code or docs. Challenge partial answers; record both halves' answers and gaps in the explainer's Recap; commit and push.
8b. **Journal draft** (learning WPs, ADR-034). An agent drafts `docs/journal/wp-$wp.md` from the explainer's Decision, Step log and Recap: front matter `wp`, `title`, `status: draft`, `date`, `locale: en`; 400 to 700 words in the owner's voice (What I built, What I learned with the real gaps from the check questions, What I would change, Next); every guessed opinion marked `<!-- owner: check -->`. Show it to the owner, apply their corrections, commit it in the WP's PR. The owner never writes it from scratch.
8c. **Study backlog.** Review this WP's lines in `docs/learning/study-backlog.md`: merge duplicates into their theme, mark the ones the explain-back showed are now solid, add what the Recap's gaps add.
8d. **Process retro.** Read the frictions the WP logged in the explainer's Step log (each with a status). For every one still open, propose the fix to the owner and, on a yes, make it in one `chore/` PR from `main` (skills, rules, `AGENTS.md`, `docs/sessions.md`); open the port PR in `project-kit` for generic process changes at the same time. Update each friction's status with the PR. The step log is the memory of the flow: a new session, local or cloud, patches the flow from it, never from a past conversation. Also count the always-loaded instructions: `CLAUDE.md`, `AGENTS.md` and every `.claude/rules/*.md` without `paths:` front matter. Claude Code's memory docs target under 200 lines per instructions file, because longer files cost context and lower adherence; when the total passes 200 lines, propose what to move out (a path-scoped rule, a skill, a linked doc) as part of the same retro.
9. **Merge order.** List the open PRs (`gh pr list` or the GitHub tools), which touch the same shared files (`docs/sessions.md` "Two sessions in parallel"), and the order to merge them. Say "ready to merge" only after the last push, naming the head commit.
9b. **Kit sync.** If `docs/process/kit-backlog.md` lists ports, port them to `project-kit` in one `chore/` PR (clone it to the scratchpad when it is not attached) and clear the lines.
10. **Next.** Tell the owner to `/clear` (or start a new session) once this PR is merged, and print the "start the next work package" prompt from `docs/sessions.md`.
