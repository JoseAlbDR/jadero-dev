# Dev containers

`compose.dev.yml` runs the two dependencies the apps need on a laptop; the apps themselves run on the host with `pnpm dev`.

- Postgres 18 with pgvector (Debian 13, the same image reference as the server's `compose.ops.yml`) on `127.0.0.1:5432` (host port `POSTGRES_PORT`): databases `content_dev`, `agent_dev`, `contact_dev`, each owned by the role of the same name (`content_dev`, `agent_dev`, `contact_dev`, password equal to the name) and closed to the others, plus `content_reader_dev`, the read-only login role of api's public reads (a member of the group role `content_reader`, which api's migrations grant SELECT to). Superuser `postgres`.
- RabbitMQ 4 on `127.0.0.1:5672` (AMQP, host port `RABBITMQ_PORT`) and `http://localhost:15672` (management UI, user `dev`, host port `RABBITMQ_MANAGEMENT_PORT`). Vhost `dev` with the users `api` and `agent`, the exchanges and every queue are loaded from `infra/rabbitmq/definitions.json`, which `pnpm --filter @jadero/messaging topology` generates from `packages/messaging/src/topology`. After changing the topology, restart the broker: `docker compose -f infra/compose/compose.dev.yml restart rabbitmq`.
- The servers' broker (one RabbitMQ, vhosts `/prod` and `/staging`, WP-8 D4) uses `infra/rabbitmq/server/`, generated by the same command: `rabbitmq.conf` loads every file of `definitions/` (`prod.json`, `staging.json`, the topology without users, so RabbitMQ never creates `guest`), and `permissions.tsv` lists each user's tags and permissions. `infra/rabbitmq/provision-users.sh` converges the users from it on every deploy: `RABBITMQ_CONTAINER=<container> infra/rabbitmq/provision-users.sh [prod|staging [<user>]]` (a deploy passes its own service's user, `api_staging`, so it needs and sets only that password), with one password variable per user (`RABBITMQ_API_PROD_PASSWORD`, `RABBITMQ_AGENT_PROD_PASSWORD`, `RABBITMQ_API_STAGING_PASSWORD`, `RABBITMQ_AGENT_STAGING_PASSWORD`, `RABBITMQ_OPS_ADMIN_PASSWORD`), read from its environment and passed to `rabbitmqctl` on stdin. It creates or re-passwords each user, sets its tags and permissions, deletes `guest`, and only warns about users the file does not list and about queues the vhost's definitions do not declare (see "Retiring a consumer" below). Dev keeps its users in `definitions.json`.
- Every `api` and `agent` deploy also imports its release's `definitions/<env>.json` into the running broker before migrate (ADR-053), with `RABBITMQ_CONTAINER=<container> infra/rabbitmq/import-definitions.sh prod|staging`: `rabbitmqctl import_definitions` on stdin, then a bounded wait (`RABBITMQ_IMPORT_TIMEOUT`, default 60 s) until every queue of the file is listed with its declared type. The import adds and updates, never deletes, and overwrites a policy of the same name, so `deploy.sh` records the newest imported `messaging` version as `MESSAGING_VERSION` in `versions.env` (before the import, since the broker is shared state) and skips a release whose version is older. A queue's type never changes in place: RabbitMQ 4.3.6 accepts such an import and silently keeps the old type, so the script fails the deploy instead; a queue that needs another type is a new name.
- Start with `pnpm dev:up` (waits for both healthchecks), stop with `pnpm dev:down`. Connection strings for the apps are in the root `.env.example`.
- Provisioning is `infra/postgres/provision.sql`, the same convergent script the servers and the integration tests run (WP-8 D4). `init/01-provision.sh` runs it with `env=dev` and the fixed dev passwords when the `pgdata` volume is empty. After `provision.sql` changes, run it again on the existing volume with `pnpm dev:provision`: it creates what is missing and sets the rest again, and keeps the data. Only a role or database renamed in the script needs a reset, since the old one stays behind: `docker compose -f infra/compose/compose.dev.yml down -v`, then `pnpm dev:up` (this deletes all local data). WP-8 renamed the roles (`content` became `content_dev`) and moved the image from Debian 12 to Debian 13, whose newer glibc changes the collation version Postgres recorded in each database (it warns `collation version mismatch` and text indexes may sort differently), so a volume from before it needs that reset once, then `pnpm db:migrate` and `pnpm --filter @jadero/api db:seed`.
- All passwords here are fixed dev values for local use only; ports bind to `127.0.0.1`, so nothing is reachable from the network.
- Host ports: when another project already holds 5432, 5672 or 15672, set `POSTGRES_PORT`, `RABBITMQ_PORT` or `RABBITMQ_MANAGEMENT_PORT` in the shell for every compose command, for example `POSTGRES_PORT=55432 pnpm dev:up` (and the same for `pnpm dev:down`, `pnpm images:up` and `pnpm images:down`). Compose reads them from the shell, or from a gitignored `infra/compose/.env` that you create: with `-f`, the project directory is the compose file's directory, so the root `.env` is never read. Only the host side moves; the containers keep 5432 and 5672 on the Compose network, so `compose.images.yml` needs no change. The apps on the host must use the same port in their `.env`: `DATABASE_URL` and `DATABASE_READ_URL` in `apps/api/.env`, `DATABASE_URL` in `apps/agent/.env`, `RABBITMQ_URL` in both.

If RabbitMQ fails with `Error when reading /var/lib/rabbitmq/.erlang.cookie: eacces`, an older start left a root-owned cookie in the anonymous volume: `docker compose -f infra/compose/compose.dev.yml down -v`, then `pnpm dev:up`.

`compose.images.yml` runs the services from their production images on top of `compose.dev.yml` (WP-7): `api`, `api-worker`, `agent`, `agent-consumer` and `web`, each read-only, without capabilities or new privileges, with a size-capped `tmpfs` and its ADR-027 memory limit, after its `*-migrate` one-off exits 0. `pnpm images:up` builds the images and waits for every healthcheck, `pnpm images:down` removes the containers (stop `pnpm dev` first: the ports are the same). `scripts/compose-hardening.test.mjs` fails when a service loses any of this.

## Service projects (the server)

`compose.services.yml` holds every process type of `api`, `agent` and `web` for the servers, with the hardening of `compose.images.yml` (read-only, no capabilities, no new privileges, a size-capped `tmpfs`, the ADR-027 `mem_limit`) plus rotated logs. It never runs alone: `compose.staging.yml` and `compose.prod.yml` add only what differs, so the two environments cannot drift apart (WP-9 step 2, ADR-053):

| | `compose.staging.yml` | `compose.prod.yml` |
|---|---|---|
| Project | `jadero-staging` | `jadero-prod` |
| `web` | `127.0.0.1:3120` (nginx, `new.jadero.dev`) | `127.0.0.1:3110` (no public host until the cutover) |
| `api` | `127.0.0.1:3121` | `127.0.0.1:3111` |
| `SITE_URL` | `https://new.jadero.dev` | `https://jadero.dev` |
| Network | `jadero_staging`, external | `jadero_prod`, external |

`api-worker`, `agent` and `agent-consumer` publish nothing; Uptime Kuma reads their health on the environment's network. Each project joins only its own ops network (the default network of the project, `external: true`), where Postgres and RabbitMQ answer by name and `pg_hba.conf` accepts only that environment's roles.

The deploy (`deploy.sh`, as root, from the files of the release being deployed) runs, for `api` on staging:

```sh
JADERO_ENV=staging API_IMAGE=... AGENT_IMAGE=... WEB_IMAGE=... \
  docker compose --project-name jadero-staging --profile api \
  -f infra/compose/compose.services.yml -f infra/compose/compose.staging.yml ...
```

- Each process type joins its service's profile (`api`, `agent`, `web`) and the deploy activates only the deployed service's, so Compose loads only that service's env file: the first `agent` deploy works before `api.env` and `web.env` exist. Compose still interpolates every image variable, so `deploy.sh` takes them from `versions.env` and fills one not deployed yet with the inert `jadero.invalid/not-deployed` (never the deployed service's own). One value, the environment word, gives `JADERO_ENV`, the overlay and the project name.

- `API_IMAGE`, `AGENT_IMAGE`, `WEB_IMAGE` come from `versions.env` as digest references (`ghcr.io/josealbdr/jadero-dev-api@sha256:...`), never tags; a missing one stops Compose before any container starts.
- `JADERO_ENV` (`staging` or `prod`) names the folder of the rendered env files and fills the role, user and vhost names inside them; it must match the overlay.
- Each service reads `/srv/jadero/<env>/<service>.env`, rendered by `op inject` from `infra/env/<service>.env.tpl` right before `up` (root, mode 600). The templates hold only 1Password references for secrets (`<item>-$JADERO_ENV`, the items of "Ops stack" below, so a rotation changes one item) and plain values otherwise: `NODE_ENV=production`, `LOG_LEVEL=info`, `OTEL_TRACES_EXPORTER=none` until a collector runs on the server, `HEARTBEAT_INTERVAL_MS=60000`, fake AI providers. `op inject` resolves `$JADERO_ENV` only inside a reference and leaves `${JADERO_ENV}` elsewhere to Compose, which interpolates env file values.
- Every process type of a service reads the same file and blanks the credentials it does not use (`environment: { RABBITMQ_URL: "" }`, which wins over `env_file`): `api` never holds the broker user, `api-worker` never holds the read-only role, only `agent-consumer` holds agent's broker user.
- After `up --wait` returns healthy, the release's `infra/scripts/smoke-deploy.sh <env> <service> <since> <deployed>` decides `verified` (WP-9 D7): `ready` (the process types' `/health/ready` on 127.0.0.1, from the host for `api` and `web`, with the image's own probe inside the container for the others), `pages` (`/<locale>/` for es, en, de, path web and api), `content` (`/api/v1/content/en/projects`, path api), through the edge on staging and on 127.0.0.1 in production, and `ping` (path api and agent: `jadero/api`'s heartbeat in `agent_<env>` newer than the moment `up --wait` returned, read-only, up to 90 s). A check runs only for a service on its path, and is skipped while another service on it is not deployed yet: the journal then says `verified smoke-passed-partial-<checks>`.

`scripts/compose-hardening.test.mjs` fails when a process type loses the hardening, its limit, its image variable or its env file, keeps a credential it does not read, publishes from the shared file, when an overlay publishes a worker or moves a port off `127.0.0.1`, joins another network or sets anything but ports and `SITE_URL`, when a template holds a secret value, a reference in a comment or an item `ops.env.tpl` does not provision, or when a process type misses a variable its config requires. Each service's `release-inputs.txt` lists a hash of its entries in these files, its template and (for `api` and `agent`) the provisioning and topology files, so a change to them releases the service (`pnpm release-inputs`).

## Ops stack (the server)

`compose.ops.yml` is the server's Compose project `jadero-ops` (WP-8 D4, ADR-050 restating ADR-027): one Postgres and one RabbitMQ shared by production and staging, Umami and Uptime Kuma. It is operated by the owner on the server, never by an agent and never on a laptop except for a throwaway test under another project name (`-p`).

- **Isolation.** Three Docker networks with fixed names and subnets: `jadero_prod` (172.30.1.0/24), `jadero_staging` (172.30.2.0/24), `jadero_ops` (172.30.3.0/24, Umami). Postgres joins all three; RabbitMQ joins prod and staging only (nothing on `jadero_ops` speaks AMQP); Uptime Kuma joins prod and staging; the `jadero-prod` and `jadero-staging` projects (WP-9) join their own network as `external`. `infra/postgres/pg_hba.conf`, mounted read-only, accepts each role only from its environment's subnet with `scram-sha-256`, and the superuser only over the socket inside the container (peer); `scripts/compose-hardening.test.mjs` fails when a role's subnet is not its environment's network, and `packages/testing/test/provision.int.test.ts` boots Postgres with the file and fails when any line does not parse. No database or broker port is published; the RabbitMQ management UI, Umami and Uptime Kuma bind to `127.0.0.1` only (Q2 B: nginx proxies their public paths, the admin screens are reached over a tunnel). Because these networks are shared, stop the service projects before `docker compose ... down` of the ops stack, or the network removal fails.
- **Hardening.** Every image pinned by digest, `no-new-privileges`, every capability dropped, a read-only root filesystem with size-capped `tmpfs`, the ADR-027 `mem_limit` (Postgres 1,024 MB with shared buffers at 256 MB, RabbitMQ 256 MB with its memory alarm at 200 MiB in `infra/rabbitmq/server/rabbitmq.conf`, Umami 300 MB, Uptime Kuma 200 MB), a healthcheck, `restart: unless-stopped` and rotated logs (the `local` driver, 3 files of 10 MB per container). Postgres and RabbitMQ get 60 seconds to stop cleanly before Docker kills them. RabbitMQ has a fixed host name, so its data folder (users, queues) survives a recreated container. `scripts/compose-hardening.test.mjs` fails when a service loses the pin, the limit, the healthcheck or the `127.0.0.1` bind, publishes a database, broker or Erlang port, takes a privilege, stops rotating its logs, when Postgres or RabbitMQ lose their stop grace period, when RabbitMQ joins `jadero_ops`, or when Postgres or RabbitMQ stop matching `compose.dev.yml`.
- **Secrets.** Rendered on the server from `infra/env/ops.env.tpl` (1Password references only, vault `jadero-ops`) by `op inject` into `/srv/jadero/ops/ops.env`, root, mode 600; the command is in the template's header. Compose reads it with `--env-file` and gives each container only its own variables; a missing one stops Compose before any container starts.

The items to create in the `jadero-ops` vault, each a password item with the value in its `password` field, generated with letters and digits only (no symbols), 32 characters or more:

- `postgres-superuser`
- `postgres-content-prod`, `postgres-content-reader-prod`, `postgres-agent-prod`, `postgres-contact-prod`
- `postgres-content-staging`, `postgres-content-reader-staging`, `postgres-agent-staging`, `postgres-contact-staging`
- `postgres-umami`, `umami-app-secret`
- `rabbitmq-api-prod`, `rabbitmq-agent-prod`, `rabbitmq-api-staging`, `rabbitmq-agent-staging`, `rabbitmq-ops-admin`

RabbitMQ's Erlang cookie needs no item: the broker generates it on first boot into its data volume, and only `rabbitmqctl` inside the same container uses it.

**Backups.** Every database, the RabbitMQ definitions export and Uptime Kuma's data volume are backed up nightly with restic to Backblaze B2 by `infra/scripts/backup.sh` under the systemd units in `infra/systemd/`; its secrets come from `infra/env/backup.env.tpl` (its own items in the same vault). The setup, the restore drill and a real restore: `docs/runbooks/restore.md`. The script finds the containers by their Compose names (`jadero-ops-postgres-1`, `jadero-ops-rabbitmq-1`, `jadero-ops-uptime-kuma-1`): renaming the project or a service breaks it, and `scripts/backup-scripts.test.mjs` fails first.

### First start and provisioning

Provisioning is not done by the containers at boot (no `docker-entrypoint-initdb.d`): it is an explicit, convergent run, repeated on every deploy (WP-9) and after any change to `provision.sql`, `pg_hba.conf` or `permissions.tsv`. As root on the server, from the repository checkout (`/srv/jadero/<checkout>` below):

```sh
cd /srv/jadero/<checkout>
set -a; . /srv/jadero/ops/ops.env; set +a          # the rendered secrets, in this shell only
compose="docker compose --env-file /srv/jadero/ops/ops.env -f infra/compose/compose.ops.yml"
$compose up -d --wait postgres rabbitmq
```

Postgres, once per environment. `docker exec -e NAME` without a value copies `NAME` from the caller's environment, so no password is ever in an argument list (`ps` shows those to every user); the `NAME=value` assignments before `docker exec` are shell assignments, not arguments:

```sh
pg=jadero-ops-postgres-1
for env in prod staging; do
  E=${env^^}
  v() { local n="${E}_$1"; printf '%s' "${!n}"; }
  CONTENT_DB_PASSWORD="$(v CONTENT_DB_PASSWORD)" \
  CONTENT_READER_DB_PASSWORD="$(v CONTENT_READER_DB_PASSWORD)" \
  AGENT_DB_PASSWORD="$(v AGENT_DB_PASSWORD)" \
  CONTACT_DB_PASSWORD="$(v CONTACT_DB_PASSWORD)" \
    docker exec -i -u postgres \
      -e CONTENT_DB_PASSWORD -e CONTENT_READER_DB_PASSWORD -e AGENT_DB_PASSWORD -e CONTACT_DB_PASSWORD \
      "$pg" psql --no-psqlrc --quiet -v env="$env" -d postgres < infra/postgres/provision.sql
done
docker exec -i -u postgres -e UMAMI_DB_PASSWORD "$pg" \
  psql --no-psqlrc --quiet -v env=ops -d postgres < infra/postgres/provision.sql
```

A deploy runs the same file with `-v service=api` (or `agent`): it converges only that service's roles, with the passwords taken from the env file the deploy just rendered, so a deploy of one service never re-passwords another's role (WP-9 D4).

RabbitMQ users, per environment (each run also converges `ops_admin`):

```sh
RABBITMQ_CONTAINER=jadero-ops-rabbitmq-1 infra/rabbitmq/provision-users.sh prod
RABBITMQ_CONTAINER=jadero-ops-rabbitmq-1 infra/rabbitmq/provision-users.sh staging
```

Then the rest, and the check:

```sh
$compose up -d --wait
$compose ps
```

Before the first `up`, check the memory: `free -m` and the other projects' use against the four limits above (about 1.8 GB together); if it does not fit, stop and decide first. Umami starts with the account `admin` / `umami` and Uptime Kuma lets the first visitor create its admin: create both admin accounts over the tunnel, with passwords from 1Password, before any public nginx site points at them.

### Retiring a consumer

The import of the definitions (at boot and by each deploy) only creates and updates, and `provision-users.sh` never deletes a queue or a user: removing a consumer from the topology leaves its queue on the broker, still bound and still filling with every new event (publishers do not know who consumes). On each run the script warns about every queue on the vhost that the definitions do not declare, with its counts:

```text
provision-users: WARN queue agent.retired on /prod is not in the definitions (3 messages, 0 consumers); left in place
```

That warning is the reminder. Retiring a consumer is a deliberate sequence, never a side effect of a deploy, and its order matters: the queue reaches 0 only once nothing feeds it. The producer does not know its consumers, so while the binding exists every new event still lands in the queue; stopping the consumer first and then waiting for a drain never reaches 0 with a live producer, because the copies keep arriving and nobody takes them.

1. Remove the queue and its bindings from the topology in `packages/messaging/src/topology`, regenerate (`pnpm --filter @jadero/messaging topology`) and deploy. The additive import deletes nothing, but no later import re-creates them, and the warning above starts. The service user's read right is generated from its service's queues, so this deploy also drops its right on the retired queue: if the consumer can no longer read it, drain in step 3 with a shovel or as `ops_admin` instead.
2. Remove the binding by hand as `ops_admin` (`rabbitmqctl` has no unbind command). The image has no `curl`, but it ships `rabbitmqadmin` 2.35.0, which calls the management API from inside the container; the credentials go in through the environment, never in an argument list:

   ```sh
   RABBITMQADMIN_USERNAME=ops_admin RABBITMQADMIN_PASSWORD="$RABBITMQ_OPS_ADMIN_PASSWORD" \
     docker exec -e RABBITMQADMIN_USERNAME -e RABBITMQADMIN_PASSWORD jadero-ops-rabbitmq-1 \
     rabbitmqadmin --non-interactive --vhost /prod delete binding --source jadero.events \
     --destination-type queue --destination <queue> --routing-key <routing key>
   ```

   The same call over HTTP (through the tunnel, `docs/runbooks/server-access.md` 2a) is `DELETE /api/bindings/%2Fprod/e/jadero.events/q/<queue>/<properties key>`: the vhost URL-encoded (`/prod` written as is answers 405), and the last segment is the binding's `properties_key`, which equals the routing key only when the binding has no arguments (with arguments it is `<routing key>~<hash>`, and the routing key answers 404). Read it first with `GET /api/bindings/%2Fprod/e/jadero.events/q/<queue>` or `rabbitmqadmin ... list bindings`. The generated bindings carry no arguments. From here no new copies arrive: an event with that routing key that no other queue binds goes to `jadero.unrouted` through the exchange's alternate exchange. Checked on the dev broker, same image, in WP-9 step 6d (`docs/runbooks/deploy.md`, section 9).
3. Let the still running consumer drain the queue to 0 messages (watch the warning's count). Or move the messages to the consumer that takes over (a shovel), or purge them (`rabbitmqctl purge_queue -p /prod <queue>`) only if they are not needed, and write down why.
4. Stop and remove the consumer (its process type) once the queue is empty.
5. Delete the queue, its DLQ and its wait queues (their bindings go with them), its policies and, when the service has no queue left, its user with its permissions: `rabbitmqctl delete_queue -p /prod <queue>`, `rabbitmqctl clear_policy -p /prod <queue>`, `rabbitmqctl delete_user <user>`. The next run no longer warns.
