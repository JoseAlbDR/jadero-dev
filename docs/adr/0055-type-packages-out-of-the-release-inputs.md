# ADR-055: Type packages out of the release inputs

**Status:** Accepted (owner, 2026-10-23). Supersedes ADR-049 for one line only: the "Dependency-only releases" line that says what `apps/<service>/release-inputs.txt` lists. Everything else in ADR-049 is restated unchanged (section "Unchanged"); read ADR-049 for its full text.

## Context

ADR-049 says each service keeps `apps/<service>/release-inputs.txt`, "its production dependency closure (`name@version`, one per line)", and that a unit test in `pnpm verify` fails when it is stale. Renovate PR #149 bumped `@types/node`. That package reaches `api` and `agent` as a production dependency: `@opentelemetry/instrumentation-pg` depends on `@types/pg`, which depends on `@types/node`. So the bump changed both files, and since the hosted Renovate cannot run the regenerate command, the pull request turned `verify` red until someone regenerated the files by hand. Had the bump been titled `fix(deps)`, it would also have released both services.

A type package holds `.d.ts` files only. Node never loads them, so a new version of one never changes what a service runs.

## Considered options

- *A. Keep listing type packages.* Pros: the file is the full production closure, exactly as ADR-049 words it. Cons: every type-only bump makes the files stale (a red `verify` and a manual regeneration), and a `fix(deps)` one releases services whose images run the same code.
- *B. Leave `@types/*` out of the listed closure.* Pros: type-only bumps leave the files as they are, so no CI failure, no regeneration and no release. Cons: the file is no longer every package the production install contains.
- *C. A workflow that regenerates the files on Renovate pull requests.* Pros: removes the manual step for every dependency bump, not only type ones. Cons: a commit pushed with `GITHUB_TOKEN` starts no workflows, so it needs a GitHub App token; it still releases services for a type-only bump. Still planned as a separate chore; it does not replace B.

## Decision

B. `scripts/release-inputs.mjs` leaves every package whose name starts with `@types/` out of the listed closure. The walk still goes through type packages, because some depend on runtime packages (`@types/pg` depends on `pg-types` and `pg-protocol`). `pnpm deploy --prod` installs those in the image whoever pulled them in, so they stay listed.

The changed line of ADR-049, as it now reads: each service keeps `apps/<service>/release-inputs.txt`, its production runtime dependency closure (`name@version`, one per line, type packages `@types/*` left out), regenerated by one command; a unit test in `pnpm verify` fails when it is stale.

## Unchanged

Restated from ADR-049 without change: the image scanning gate (A), the registry choice (B, private images pulled with the deploy job's token), the release token (A, with the GitHub App as fallback), the release components, the rest of the dependency-only releases decision (one file per service, regenerated by one command, the staleness test in `pnpm verify`, Renovate's `semanticCommitType: fix` for production dependency and base image updates), the provenance, the move of the staging deploy to WP-9, the restated parts of ADR-048 and ADR-025, the consequences and the pattern names.

## Consequences

- The file lists the runtime closure a service ships, not every package its production install contains.
- A type-only bump no longer makes the files stale and releases nothing, whatever its commit type.
- Regenerating the files with this rule changes them once, so the pull request that introduces it releases `api`, `agent` and `web` once.
- A runtime package reached only through a type package is still listed, so a bump of it still releases the service.
- The regenerate workflow for Renovate pull requests (option C) stays a separate chore.

## Pattern names

Declared inputs (hermeticity), generated file with a staleness test, false-positive trigger (a change that cannot affect the output should not trigger a release), decision record that supersedes rather than edits.
