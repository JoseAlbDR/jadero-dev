# Backups and restore

How the server's data is backed up, how the owner sets it up once, how the restore drill runs and how a real restore is done. Background: ADR-027 "Backups" (the scope), ADR-050 and ADR-051 "Backup destination" (Backblaze B2, retention, the drill as acceptance), ADR-017 (the chat checkpoints stay out), the WP-8 explainer, D7, D8 and Traces 2 and 3a.

Placeholders stand for values that stay out of this repo: `<region>` (the bucket's region code, for example `eu-central-003`), `<bucket>`, `<checkout>` (the repository checkout on the server, as in `infra/compose/README.md`), `<personal-account>` (the owner's personal 1Password account, never the employer's), `<run>` (a run tag such as `run-20261018T023000Z`).

## 1. What runs, and what it saves

- **Nightly, 02:30 server time** (`jadero-backup.timer`, up to 10 minutes of random delay, `Persistent=true` so a night missed while the server was off runs at the next boot), `jadero-backup.service` runs `/srv/jadero/bin/backup.sh` as root. Sources: `infra/scripts/backup.sh`, `infra/systemd/`.
- **What one run saves**, each item its own restic snapshot, all tagged with the run's tag `run-<UTC time>`:
  - `uptime-kuma-data.tar`: Uptime Kuma's data folder (its SQLite database: the monitors, the status page, the push monitor of this backup). Kuma is stopped for the seconds the copy takes, so the copy is consistent, and started again however the script ends.
  - `<database>.dump`: every database of the ops Postgres, found at run time in `pg_database` (not the templates, not `postgres`), so a new database is never forgotten. `pg_dump -Fc` (custom format: one table can be restored alone). The data of the chat checkpoint tables (schema `checkpoints`) is left out (ADR-017); their structure is kept.
  - `rabbitmq-definitions.json`: the broker's definitions export (vhosts, users with their password hashes, queues, bindings, policies). Queued messages are not backed up: every producer resends from its outbox and every consumer is idempotent (ADR-027).
  - `backup-run.complete`: written last, only when every item above was saved. It lists the run's items, so a restore can pick a whole night.
  - The media volume joins the set when WP-17 adds it.
- **Fail loudly.** restic runs each dump command itself (`--stdin-from-command`) and saves no snapshot when the command fails. A failed item does not stop the others, but the run exits 1, skips the retention step and sends no heartbeat.
- **Retention**, per item: `restic forget --keep-daily 7 --keep-weekly 4 --prune`, after a run where everything was saved.
- **Heartbeat** (a dead man's switch, D8): the last step pings the Uptime Kuma push monitor `jadero backup`. No ping by morning means the monitor goes down and alerts. The URL carries a token: the script never prints it.
- **Weekly check**, Sundays 05:00 (`jadero-backup-check.timer`): `restic check --read-data-subset=5%` reads back a random 5% of the stored data, so a corrupt pack is found before a restore needs it.
- **Where:** a private Backblaze B2 bucket in EU Central, through restic's S3 backend (`s3:https://s3.<region>.backblazeb2.com/<bucket>`). restic encrypts on the server before anything leaves; B2 only ever holds ciphertext. The repository password and the B2 key live in 1Password (vault `jadero-ops`), so a restore works from the laptop when the server is gone.
- **The two numbers.** RPO (how much data a restore may lose): up to one day, the timer's period. RTO (how long until it works again): measured by the drill (section 3), never guessed.

## 2. One-time setup (owner)

### 2a. Backblaze B2 (the console; the session gives each field)

1. An account with its data region set to EU Central (chosen at sign-up, it cannot change later).
2. A private bucket, Object Lock off. restic encrypts already, so B2's own encryption adds nothing.
3. The bucket's lifecycle rule: keep only the last version of a file. B2 keeps every version by default, so the data restic prunes would otherwise stay and be billed.
4. An application key restricted to this bucket, read and write. B2 shows the key once.
5. Caps and alerts: an alert well before the free 10 GB of storage and the free daily transactions (ADR-050 consequences). Check what the console shows for both and note it in the step log.
6. The bucket's details page: its S3 endpoint gives the region code for `RESTIC_REPOSITORY`.

### 2b. 1Password (vault `jadero-ops`)

| Item | Category | Field | Value |
|---|---|---|---|
| `backup-b2` | API Credential | `username` | the application key's ID |
| | | `credential` | the application key |
| | | `bucket` (text) | the bucket name |
| | | `endpoint` (text) | the bucket's S3 endpoint, `s3.<region>.backblazeb2.com`, no trailing dot |
| `backup-restic` | Password | `password` | generated by 1Password, at least 40 characters, never typed, with no single quote (`'`): the env file holds it inside single quotes |
| `uptime-kuma-backup-push-url` | Password | `password` | the push monitor's URL, with the host changed to `127.0.0.1:3101` (section 2e) |

`infra/env/backup.env.tpl` builds `RESTIC_REPOSITORY` as `s3:https://<endpoint>/<bucket>` from the `backup-b2` fields. To check the field labels without showing a value:

```bash
op item get backup-b2 --account <personal-account> --vault jadero-ops --format json \
  | jq -r '.fields[] | .label'
```

Losing this password loses every backup: nobody, Backblaze included, can decrypt them.

### 2c. restic 0.19.1 on the server

Ubuntu 26.04 ships restic 0.18.1; the pinned upstream release is installed instead, checked against its signed checksums. On the server:

```bash
cd "$(mktemp -d)"
v=0.19.1
base="https://github.com/restic/restic/releases/download/v$v"
curl -fsSLO "$base/restic_${v}_linux_amd64.bz2"
curl -fsSLO "$base/SHA256SUMS"
curl -fsSLO "$base/SHA256SUMS.asc"
# restic's release key, by its full fingerprint; check the fingerprint gpg prints.
curl -fsS 'https://keyserver.ubuntu.com/pks/lookup?op=get&search=0xCF8F18F2844575973F79D4E191A6868BD3F7A907' | gpg --import
gpg --verify SHA256SUMS.asc SHA256SUMS      # "Good signature", key CF8F 18F2 8445 7597 3F79 D4E1 91A6 868B D3F7 A907
sha256sum --ignore-missing -c SHA256SUMS     # restic_0.19.1_linux_amd64.bz2: OK
bunzip2 "restic_${v}_linux_amd64.bz2"
sudo install -o root -g root -m 755 "restic_${v}_linux_amd64" /usr/local/bin/restic
restic version                               # restic 0.19.1 ...
```

The checksum of `restic_0.19.1_linux_amd64.bz2` in the signed file is `f415415624dcc452f2a02b8c33641791a8c6d6d3b65bbb3543fcf9a25151585c`. gpg warns that the key is not certified by a trusted signature: expected, the fingerprint check is the trust.

### 2d. The env file, the repository, the scripts and the units

As root on the server, from the checkout:

```bash
cd /srv/jadero/<checkout>
OP_SERVICE_ACCOUNT_TOKEN="$(cat /etc/jadero/op-token)" \
  op inject --force -i infra/env/backup.env.tpl -o /etc/jadero/backup.env
stat -c '%U %a' /etc/jadero/backup.env        # root 600

# Create the repository once (it fails harmlessly if it exists).
bash -c 'set -a; . /etc/jadero/backup.env; set +a; restic init'

install -o root -g root -m 755 infra/scripts/backup.sh infra/scripts/restore.sh /srv/jadero/bin/
install -o root -g root -m 644 infra/systemd/jadero-backup.service infra/systemd/jadero-backup.timer \
  infra/systemd/jadero-backup-check.service infra/systemd/jadero-backup-check.timer /etc/systemd/system/
systemctl daemon-reload
systemd-analyze verify /etc/systemd/system/jadero-backup*.service    # no output
systemctl enable --now jadero-backup.timer jadero-backup-check.timer
systemctl list-timers 'jadero-backup*'
```

The env file must stay root's with no group or other access: `backup.sh` refuses to read it otherwise. A change to a script or a unit in the repo is installed the same way.

### 2e. The Uptime Kuma push monitor

In Uptime Kuma (over the tunnel, Q2 B): a new monitor of type Push, named `jadero backup`, heartbeat interval 90000 seconds (25 hours: one night plus the timer's delay and the run), no retries. Kuma shows its push URL with its own public host; nginx does not open `/api/push/` on `status.`, so store it in 1Password with the host part changed to `http://127.0.0.1:3101` (the script runs on the server). Keep the query string Kuma shows (`?status=up&msg=OK&ping=`).

Optional: a second push monitor for the weekly check (interval about 8 days), stored as `uptime-kuma-backup-check-push-url`, then add this line to `infra/env/backup.env.tpl` and render again. Without it, a failed check shows only in `systemctl --failed` and the journal.

```bash
BACKUP_CHECK_HEARTBEAT_URL='{{ op://jadero-ops/uptime-kuma-backup-check-push-url/password }}'
```


## 3. The restore drill

The acceptance test of WP-8 (ADR-050), repeated after any change to the backup and at least once per release. Everything here restores into a throwaway Postgres container with no network; the live database is only read, for the comparison.

1. **A first run by hand**, then its log:

   ```bash
   sudo systemctl start jadero-backup.service
   journalctl -u jadero-backup -n 30 --no-pager
   ```

   One `saved` line per item, `forget and prune done`, `heartbeat sent`. The `jadero backup` monitor in Uptime Kuma turns up.

2. **The snapshots** (the complete runs are listed at the end):

   ```bash
   sudo /srv/jadero/bin/restore.sh --env-file /etc/jadero/backup.env snapshots
   ```

3. **Restore the last complete night and compare.** The script prints the time the restore took (container start, download, `pg_restore` of every database), then the row count of every table next to the live one:

   ```bash
   time sudo /srv/jadero/bin/restore.sh --env-file /etc/jadero/backup.env all --compare jadero-ops-postgres-1
   ```

4. **What to compare.** Every table's count matches the live database, except:
   - the three checkpoint tables, marked `data not backed up (ADR-017)`: empty on purpose;
   - tables written since the run (`DIFFERS`): expected for rows added after 02:30; anything else is a finding.
   Also list one archive's contents, which reads it without restoring:

   ```bash
   sudo bash -c 'set -a; . /etc/jadero/backup.env; set +a; restic dump --path /content_prod.dump latest /content_prod.dump' |
     docker run --rm -i --network none pgvector/pgvector:0.8.7-pg18-trixie@sha256:9d9c930220cb9bf2f956d10a8f909cf9973d9672ca0278aef2c1e6facccad2e0 pg_restore --list | head -20
   ```

5. **The other items**: the RabbitMQ definitions and the Kuma data restore to files (mode 600) for a look:

   ```bash
   sudo /srv/jadero/bin/restore.sh --env-file /etc/jadero/backup.env dump rabbitmq-definitions.json /root/definitions.json
   sudo /srv/jadero/bin/restore.sh --env-file /etc/jadero/backup.env dump uptime-kuma-data.tar /root/kuma.tar
   sudo tar -tf /root/kuma.tar | head; sudo rm /root/definitions.json /root/kuma.tar
   ```

6. **Write down the measured restore time** (the `restored ... in Ns` line, and `time`'s total for the whole command) in the table below and, for WP-8, in the explainer's step log. That number is the RTO for the data; a full rebuild of the server adds the time of section 5.

7. **From the laptop**, to prove the restore does not need the server (section 5).

Drill record:

| Date | Where | Run | Databases | Restore time | Result |
|---|---|---|---|---|---|
| 2026-10-18 | server, then laptop (snapshots only) | `run-20261018T105626Z` | 7 (the service databases still without tables, before WP-9; `umami` with data) | 18 s restore, 24 s whole command | every count matched; `pg_restore --list` read the `umami` archive; RabbitMQ definitions and Kuma data (`kuma.db`) restored to files; the laptop listed the same 10 snapshots |

## 4. Restore for real

**Restore every database from the same night**, unless there is a reason not to. Each service's outbox marks an event as sent once the broker took it. Restore only `content_prod` to last night and `api` has forgotten posts whose events the `agent` already consumed, or the reverse: the agent misses events `api` believes it delivered, and the outbox will not resend them. Restoring all of them from one complete run puts every service back at the same moment; the daily `knowledge.snapshot.v1` (WP-14) reconciles what remains.

1. Run the drill on the run you will restore (section 3, `all --run <run>`): it proves the night restores before the live data is touched.
2. Stop the service projects (`jadero-prod`, `jadero-staging`) and Umami (`docker stop jadero-ops-umami-1`), so nothing writes while the databases are replaced; a database with an open connection cannot be dropped.
3. Run the provisioning of `infra/compose/README.md` ("Ops stack"): the roles must exist before a dump that names them as owners is restored.
4. Each database of the run, replaced (`--clean --create` drops and recreates it):

   ```bash
   sudo bash -c 'set -a; . /etc/jadero/backup.env; set +a; restic dump --tag <run> --path /content_prod.dump latest /content_prod.dump' |
     docker exec -i jadero-ops-postgres-1 pg_restore -U postgres --clean --if-exists --create --exit-on-error -d postgres
   ```

5. The provisioning again (it is convergent): grants and default privileges back as the repo defines them.
6. Uptime Kuma, only when its data is lost: stop it, copy the folder in, start it (the tar holds `data/...`, so it lands in `/app/data`):

   ```bash
   docker stop jadero-ops-uptime-kuma-1
   sudo /srv/jadero/bin/restore.sh --env-file /etc/jadero/backup.env dump --run <run> uptime-kuma-data.tar /root/kuma.tar
   sudo sh -c 'docker cp - jadero-ops-uptime-kuma-1:/app < /root/kuma.tar && rm /root/kuma.tar'
   docker start jadero-ops-uptime-kuma-1
   ```

7. RabbitMQ needs no restore in the normal case: its vhosts, queues and bindings come from the repo's definitions at boot, its users from `provision-users.sh`. The export is the record of what the broker held, for a diff or an `import_definitions` when the repo and the broker disagree.
8. Start Umami and the service projects; check `/health/ready` and Uptime Kuma.

## 5. When the server is gone

The backups live in B2 and the keys in 1Password: nothing needs the old server.

- **On the laptop** (macOS: bash, Docker and restic 0.19.1, the `darwin_arm64` file of section 2c, checked the same way with `shasum -a 256 -c` instead of `sha256sum`), from a checkout of this repository:

  ```bash
  infra/scripts/restore.sh --env-file <(op inject --account <personal-account> -i infra/env/backup.env.tpl) snapshots
  infra/scripts/restore.sh --env-file <(op inject --account <personal-account> -i infra/env/backup.env.tpl) all
  ```

  `op inject` without `-o` prints to the pipe only: the secrets never touch the laptop's disk.
- **On a new server**: prepare it as WP-8 did (server access, the ops stack, provisioning), install restic and the env file (section 2), then restore for real (section 4).

## 6. When something is wrong

- **The `jadero backup` monitor is down.** `journalctl -u jadero-backup --since yesterday`: a `FAILED` line names the item. A failed run saved what it could, kept every older snapshot and skipped retention; fix the cause and run it again by hand.
- **"repository is already locked".** Another run or the weekly check holds the lock; the scripts wait up to an hour for it. A lock left by a killed run: `restic list locks`, then `restic unlock` (it removes stale locks only), both with the env file loaded as above.
- **Uptime Kuma is down after a reboot during the backup.** The script stops Kuma for its copy and starts it again; a reboot in those seconds leaves it stopped (`unless-stopped` respects a stop). `docker start jadero-ops-uptime-kuma-1`.
- **A new database.** Nothing to do: the next run finds it in `pg_database`.
- **The check, before installing a change**: `pnpm backup:check` runs both scripts against throwaway containers (Docker); the `backup` job of `ci.yml` runs it on every pull request that touches them.
