After a merge to main

WP-1 closed on 2026-10-03: trace 3 checked with Docker on your machine (the agent role denied on content_dev, vector 0.8.7 in agent_dev), the explain-back recorded in the Recap, PR #66 squash merged, and the card moved to Done on its own.

  1. git switch main && git pull && pnpm install && pnpm verify:all. Chain with &&: if one step fails, nothing else runs.
  2. Why verify:all: pnpm verify uses --affected, which compares with main. On main nothing is affected, so it prints "No tasks were executed". On a branch, plain verify is the right command.
  3. On a branch, after merging main into it: run pnpm verify again before pushing. A merge brings files that never went through your hooks (WP-1 pushed a merge with an unformatted file from another PR).

Also waiting for you, no code: the Project views (scripts/github/README.md).

Gates in order, and why the learning comes before the merge

The decision gate is before any code: the hook refuses edits under a learning path until the explainer says decision: recorded. The explain-back gate is before the merge: the issue's acceptance list has "Explained back by the owner", and the Recap lands in the same PR, so the merged history shows the code and what you understood of it together. If a Recap is ever missed, it lands after the merge as a docs(learning) commit.

Why branches are called wp/

Versions never come from branch names. With squash merges, the PR title becomes the one commit on main; release-please reads its type (feat minor, fix patch, ! major) to version each service. The wp/NN-slug name ties the branch to its issue and lets the learning gate hook find docs/learning/wp-NN.md. Work outside a WP uses chore/, fix/ or docs/.

What a session looks like

A WP is a conversation in Claude Code inside the repo; the files are what the conversation leaves behind. The shape, with WP-3 as the example:

What you never type: a push to main, a deploy, an eval without EVAL_CONFIRMED=1. What the hooks do for you: a denied edit under a learning path while the decision is pending (that is the process, not a bug), Biome on every edit and on staged files, commitlint on every commit.

How you learn, concretely

What you learn, and why. Your job is to orchestrate agents and challenge their proposals, so the explainer sorts every concept: own it (boundaries, consistency, failure modes, data flow and privacy, observability, data modeling, the cost of changing a decision), recognize it (named patterns), or delegate it (library APIs, config, versions, in an appendix nobody asks about). For each decision you answer first, with your pick and one risk, and only then read the recommendation. Options always include one the agent would not choose and when it would win, plus what would make the decision wrong. The explain-back is interview practice: why, what else, when to change it, what happens when it fails, and the main trace drawn from memory. Your PR review is a design review on the code map. You write the journal post.

Two halves. The file is the textbook written for this WP: first principles, one trace with real payloads, named patterns, options. The session is the teacher: you ask about any paragraph or file, and the agent answers right there; at the end it asks you three or four questions and you answer in your own words (the explain-back). The gaps go to the Recap section of the file and become the raw material of the journal post.

  • The explainer is self-contained: you never open an ADR, another WP or the plan to answer. Its "How to read this file" table says exactly what to read before each question (5 to 10 minutes), and its "Named here" table says in one line what every WP or ADR it names is.
  • The session asks all the questions in one message, each with its reading pointer, the options and what changes later depending on your answer. The recommendations come in a separate block after the last question: you read it only after you have answered. A question that depends on another gets a recommendation per possible answer of the first in that block, so you answer everything in one reply.
  • Nothing is to memorize. An explain-back you cannot answer means the explainer missed something: it gets taught, added to the file and noted in the Recap, not asked again as a test.
  • A step you already know: say "known". It gets fast_path: known, no explanation, no explain-back for that step.
  • A fact marked verify in an explainer is something the agent could not confirm from a primary source. Ask it to verify at implementation time, or verify it yourself.
  • Learning survives the PR: the Recap can be written after the merge in a docs commit. Once a learning WP has run without you (as WP-1 did), do the explain-back on the next session before moving on.

With firstmate

The full guide is docs/firstmate.md: what firstmate reads and in which order, the flow mapped to its concepts, the collision table with a rule per row, and the two prompts in Continue tomorrow. In short: point firstmate's implementers at AGENTS.md; it is tool-neutral and the rules under .claude/rules/ are plain Markdown. The mapping (plan = /wp step list, approve = recorded decision, implement = one step with its log line, review = the reviewer checklist, MR = PR with Closes #) is in docs/agent-tooling.md. Two things firstmate must honor and cannot replace: the learning gate (read the explainer front matter before touching a learning path) and the ADR files (supersede, never edit). Security guardrails stay firstmate's job; the repo does not duplicate them.

Cloud sessions are fine for anything that needs no Docker and no owner presence: explainers, ADR drafts, tooling fixes, reviews. Implementation of a learning WP belongs in your local session, where you are present and Docker runs.
