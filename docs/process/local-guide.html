After a merge to main

WP-1 closed on 2026-10-03: trace 3 checked with Docker on your machine (the agent role denied on content_dev, vector 0.8.7 in agent_dev), the explain-back recorded in the Recap, PR #66 squash merged, and the card moved to Done on its own.

  1. git switch main && git pull && pnpm install && pnpm verify:all. Chain with &&: if one step fails, nothing else runs.
  2. Why verify:all: pnpm verify uses --affected, which compares with main. On main nothing is affected, so it prints "No tasks were executed". On a branch, plain verify is the right command.
  3. On a branch, after merging main into it: run pnpm verify again before pushing. A merge brings files that never went through your hooks (WP-1 pushed a merge with an unformatted file from another PR).

Also waiting for you, no code: the Project views (scripts/github/README.md).

Gates in order, and why the learning comes before the merge

The decision gate is before any code: the hook refuses edits under a learning path until the explainer says decision: recorded. The explain-back gate is before the merge: the issue's acceptance list has "Explained back by the owner", and the Recap lands in the same PR, so the merged history shows the code and what you understood of it together. If a Recap is ever missed, it lands after the merge as a docs(learning) commit.

Why branches are called wp/

Versions never come from branch names. With squash merges, the PR title becomes the one commit on main; release-please reads its type (feat minor, fix patch, ! major) to version each service. The wp/NN-slug name ties the branch to its issue and lets the learning gate hook find docs/learning/wp-N.md. Work outside a WP uses chore/, fix/ or docs/.

How you learn, concretely

What you learn, and why. Your job is to orchestrate agents and challenge their proposals, so the explainer sorts every concept: own it (boundaries, consistency, failure modes, data flow and privacy, observability, data modeling, the cost of changing a decision), recognize it (named patterns), or delegate it (library APIs, config, versions, in an appendix nobody asks about). Each decision the ADRs already took is explained as problem, example, decision, alternatives (why discarded, when each would win) and the patterns to recognize, with a diagram where it helps. You answer only the few open questions no ADR decides, before reading the recommendation, and the agent challenges your answer when it disagrees. The explain-back is interview practice: why, what else, when to change it, what happens when it fails, and the main trace drawn from memory. Your PR review is a design review on the code map. The journal post of each WP is drafted by an agent from the Recap (/wrap-wp, in docs/journal/wp-N.md) and corrected by you (ADR-034).

Two halves. The file is the textbook written for this WP: the decisions explained, one trace with real payloads, the named patterns. The session is the teacher: you ask about any paragraph or file, and the agent answers right there; at the end it asks you three or four questions and you answer in your own words (the explain-back). The gaps go to the Recap section of the file and become the raw material of the journal post.

  • You decide from the chat: the session gives each decision (problem, example, decision, alternatives, patterns), the implementation choices one line each, and the open questions with what you need to know right before each. The file keeps the same plus the traces and a "Named here" table.
  • Usually zero to two open questions, all in one message. The recommendations come in a separate block after the last question, read after you answer; a question that depends on another gets a recommendation per possible answer of the first. Your answer starts a discussion, not an order: the agent says when it would pick differently and why.
  • Nothing is to memorize. An explain-back you cannot answer means the explainer missed something: it gets taught, added to the file and noted in the Recap, not asked again as a test.
  • A step you already know: say "known". It gets fast_path: known, no explanation, no explain-back for that step.
  • A fact marked verify in an explainer is something the agent could not confirm from a primary source. Ask it to verify at implementation time, or verify it yourself.
  • Learning survives the PR: the Recap can be written after the merge in a docs commit. Once a learning WP has run without you (as WP-1 did), do the explain-back on the next session before moving on.

Starting a session

Every work package runs in a Claude Code session started in this repo, in the cloud (claude.ai/code) or on your machine. There is no other framework: AGENTS.md, CLAUDE.md and .claude/ carry the whole flow. The full guide is docs/sessions.md: what a new session reads, the differences below, and the three prompts in Continue tomorrow.

The security layer is Claude Code's permission settings (.claude/settings.json denies reading the real .env files), the learning gate and your review. A sandbox applies only when the session runs in one (cloud sessions do; a local session may not). The repo states the rules in AGENTS.md section 7.
