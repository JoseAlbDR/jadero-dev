The flow that ran end to end on WP-1 and WP-3, written down so every work package runs the same way in a Claude Code session started in the repo, in the cloud or locally. Every rule here has a file in the repo as its source (docs/agent-tooling.md, docs/local-playbook.md, docs/sessions.md); this page only orders them.

Sources of truth, in order of precedence

  2. docs/plan/report.md section 14 and docs/plan/decisions.json: the work packages, releases R0 to R7, and the 76 owner decisions as data.
  3. GitHub: epic jadero.dev v2, one issue per WP (#8 to #64), milestones R0 to R7, the Project board. The issue is the task; the PR closes it.

The ten stages of one work package

Example throughout: WP-11, Contact service, a learning WP of release R1.

1

Pick it from the board

Owner · board: Backlog → Ready

A WP is Ready when its dependencies are closed, its acceptance criteria are written in the issue and the ADRs it needs are accepted. The owner moves it to Ready. Nothing is Ready by default.

2

Start: /wp 11

Agent · board: Ready → In progress

The skill reads the WP from decisions.json, checks each dependency's issue is closed, checks the learning gate, creates wp/11-contact-service from origin/main, proposes 4 to 8 steps (each ends in a green pnpm verify and a commit) and prints the definition of done. Then it stops for the owner's go. The owner moves the card to In progress when the branch exists.

3

Learn: /learn-step 11

Agent writes, owner reads · gate closed

The skill writes docs/learning/wp-11.md: each ADR decision the WP implements explained as problem, example, decision, alternatives (why discarded, when each would win) and patterns; the few open questions (only architecture no ADR decides); the implementation choices; one concrete trace with real payloads and SQL (two on a service WP, success and failure). The same decisions, choices and questions go in the chat, so the owner decides without opening another file; recommendations come after the questions, and the agent challenges answers it disagrees with. It stops. While the front matter says decision: pending, the hook learning-gate.sh denies any edit under a learning path. The list in the hook: apps/api, apps/agent, apps/contact, apps/mcp, apps/gateway, apps/guard-classifier; packages/messaging, packages/ai, packages/agent, packages/contracts, packages/platform-nest; templates/, infra/, .github/workflows/; and the repo tooling files turbo.json, pnpm-workspace.yaml, packages/config/, .dependency-cruiser.*, lefthook.yml and commitlint.config.*. A denied edit is the process working.

Fast path (D-38): a step the owner already knows gets fast_path: known in the explainer and skips the full explainer and the explain-back.

4

Decide

Owner · gate opens

The owner answers the questions, in chat or in the file. The agent records them under Decision, sets decision: recorded and links the ADR. If the answer changes an accepted ADR, /adr first. Only now may code under the learning paths change.

5

Implement in small visible steps

Main session explains and asks, implementer agent builds (/step), owner watching

One step at a time, under the step contract (AGENTS.md section 5): name the files, the explainer paragraph and the ADR lines first, and stop if the code would depart from an ADR; write; pnpm verify green; show it running; a privacy check (logs, spans, error bodies, headers); two lines in the explainer's step log written from the diff; one check question for the owner on learning steps; one conventional commit scoped to the service (feat(contact): add outbox relay). A WP of size M or larger gets a mid-WP @agent-reviewer run. Zod at every boundary, fakes and contract suites first, Testcontainers for SQL or the broker. The owner can stop at any step and ask /explain.

6

Map: update the code map and the docs

cartographer agent through /map, as the last implementation step; then /wrap-wp

The last step of every WP brings docs/architecture/code-map.html up to date (its JSON data block, so a new box or arrow is data, not code), plus every doc the WP changed: AGENTS.md commands, the service's own AGENTS.md, docs/local-playbook.md and these process pages. The claude.ai artifacts are copies; the repo files are the source. The owner uses the map to review the design before the PR.

7

Open the PR

Agent · board: In progress → In review (automatic)

Title: the conventional commit that becomes the squash commit and the changelog line. Body from the template with Closes #19 on the first line; the Project workflow "Pull request linked to issue" moves the card to In review. No attribution footers, model names or session links anywhere. CI (WP-6, not built yet) will run lint, typecheck, unit, integration and the coverage gates of ADR-009; until then pnpm verify is the check.

8

Review, explain back, journal draft

@agent-reviewer first, then the owner, then an agent

The reviewer subagent runs its ten-point checklist (boundaries, messaging, AI and guards, OWASP LLM Top 10, testing, secrets, content rules, delivery, learning gate, docs) and reports findings with file:line and the smallest fix; it never approves. The agent fixes what it can and pushes. The owner reviews the PR. Then comes the explain-back: the owner explains the design back in their own words, and the agent records the answers and the gaps in the explainer's Recap. Then, still at /wrap-wp and before the merge, an agent drafts the journal post in docs/journal/wp-N.md from the Recap, and the owner corrects it (ADR-034).

9

Merge

Owner · board: In review → Done (automatic)

Squash merge; the branch is deleted; the issue closes through Closes #; the workflow "Item closed" moves the card to Done. release-please opens or updates the release PR for the service from the squash commit; merging that PR tags the version and builds the image.

10

Ship

Owner present

Deploy to staging, then production (agents never run deploy scripts). The journal post, drafted and corrected before the merge, is published from the admin once WP-39 exists. The definition of done in the issue is the checklist: tests green with gates, docs updated where a rule or command changed, deployed to staging, changelog entry present.

What the explain-back is, and what it is not

The explain-back is the owner explaining the design back, in their own words, after the PR review (stage 8). The agent asks only about what the explainer taught, and writes the answers and any gaps in the explainer's Recap section. It is not the decision questions of stages 3 and 4: those are choices the owner makes before any code exists. An "I don't know" in the explain-back means the explainer missed something, and the explainer gets fixed. A step marked fast_path: known has no explain-back.

Interview form, and what the learning aims at. The owner orchestrates agents and challenges them, so explainers label concepts Own (boundaries, consistency, failure modes, data flow and privacy, observability, data modeling, cost of change), Recognize (named patterns) or Delegate (library APIs and config, in an appendix that is never asked). For each decision the owner answers first, with a pick and one risk, before reading the recommendation; options include one the agent would not choose and when it would win, plus what would make the decision wrong. The explain-back asks, for each major piece: why this way, what else, when to change it, what happens when it fails, and the owner draws the main trace from memory before comparing with the code map.

Session hygiene

Model and effort

The repo pins no model. For the main session Opus 5.5 at high effort for learning WPs, medium for frontend and chores. The reviewer agent inherits the session model at high effort. The orchestrator pattern keeps the main session for the conversation with the owner: drafting, building, mapping and research go to agents, so its context stays small (WP-5's single session reached about 700k tokens).

When to compact

  • After /wp and before /learn-step is rarely needed; the two are short.
  • After the owner records the decision and before implementation starts: the explainer is in the file, so the reasoning can leave the context.
  • After the PR is open and the reviewer has reported: keep only the PR number, the open findings and the step log.
/compact Keep: branch and WP id, the recorded decision (file path), the step list with done marks, open reviewer findings, the owner's rules (Spanish in chat, English in files, no em dashes, no attribution footers, learning first). Drop explanations already saved in docs/learning/.

Cloud session versus local

In a cloud session gh is not authenticated as the owner, so the seed script, Project edits and anything that needs the owner's token run locally. Pushes and PRs work through the GitHub app. Locally, everything in this page works as written and the hooks run in the owner's Claude Code.

Sessions

Every work package runs in a Claude Code session started in this repo, in the cloud (claude.ai/code) or on the owner's machine. There is no other framework: AGENTS.md, CLAUDE.md and .claude/ carry the whole flow. The full guide is docs/sessions.md.

What differsCloud sessionLocal session

ArtifactsRepublishes the code map and the process pagesEdits the repo files; the next cloud session republishes

Four prompts in docs/sessions.md, copied verbatim in the local guide:

  • Start the next work package: the same prompt for every backend or learning WP. The session lists the WPs whose dependencies are closed, recommends the next backend one and waits for the owner's choice; then /wp, /learn-step, the decision, /step per step, /map and /wrap-wp (PR, review, explain-back).
  • A frontend work package: result-only, no learning gate; builds to the design system, stops only for product or content questions, a screenshot per step, then the PR and the review.
  • Resume a work package in a new session: read the explainer and the branch log, say where we are and which step is next, wait for the go.
  • A chore outside a work package: a chore/ branch, one change, pnpm verify green, one commit, a PR without Closes.

A backend and a frontend WP can run at the same time, one session each, on their own branches. They share the lockfile, the catalog, a few root config files, the code map and the status lines; the PR that merges second brings main in, regenerates the lockfile with pnpm install (never by hand), runs pnpm verify and pushes.

Daily checklist, local session

  1. git switch main && git pull && pnpm verify:all. Open the board; pick the Ready card or move one there.
  2. Start Claude Code in the repo. The SessionStart hook prints the branch, the gate status and where the decisions are.
  3. /wp NN. Read the step list; say go, or edit it.
  4. /learn-step NN (learning WPs). Read the explainer. Ask /explain for anything unclear. Answer the question.
  5. /step NN M: read the explanation, watch the demo, answer the check question. Repeat.
  6. /map, then /wrap-wp NN: docs, artifacts, PR, @agent-reviewer and fixes, explain the design back (Recap); merge.
  7. Close the session with the explainer's Recap filled and the card in Done.

The WP-1 trial

WP-1 (Repo foundation) ran end to end from a cloud session on 2026-10-03: /wp 1 and /learn-step 1, seven implementation steps delegated one at a time to subagents on Opus 5.5 with the main session as reviewer, PR #66 with Closes #9, the reviewer agent (verdict "fix first", one high finding: no rule stopped a service importing another service's code), the fixes, and a green pnpm verify (5 tasks, FULL TURBO on the second run). /wp 3 and /learn-step 3 then ran on the first service WP. Stages 2 to 7 work as designed. The owner then closed it locally: the Docker stack and trace 3 passed after one fix (RabbitMQ crashed on .erlang.cookie: eacces; it now runs as user: rabbitmq), the explain-back went into the Recap with two gaps to re-ask at WP-3, the squash merge closed issue #9 and the card moved to Done on its own.

What WP-1 did not do well: decisions were taken on the owner's behalf ("take the recommendation") and the explain-back came after the implementation instead of during it. WP-3 runs the canonical flow end to end: the owner answers each question before any code.

What the trials changed in the tooling (PRs #65 and #67)

  • /wp works without a logged-in gh, names the source of the definition of done, marks n/a items, and has a rule for stacking a branch on an unmerged dependency.
  • /learn-step may query npm, Docker Hub and nodejs.org through Bash, marks unverified behavior verify, asks for two traces on a service WP, and the template gained Facts checked and Proposed steps sections.
  • The learning gate also covers the repo tooling files, packages/platform-nest and templates/.
  • Cloud sessions commit as the tool; branch authors are reset to the owner before a PR so a squash adds no co-author trailer.
  • Turborepo's self-written agent block in AGENTS.md is turned off (agentGuidance: false); its .turbo/ metadata is excluded from lint inputs so the cache hits.
  • The seed marks staging and changelog items n/a for R0 work packages.

What the WP-1 close-out changed (PR #68)

  • pnpm verify:all: --affected compares with main, so on main plain verify ran 0 tasks.
  • Run pnpm verify after merging main and before pushing: a merge was pushed with an unformatted file from another PR.
  • Untracked package.json on main blocked git switch; setup commands are chained with &&.
  • Biome 2.5 moved recommended to preset; Turborepo is on 2.11.7.

The WP-3 run

WP-3 (Service platform and API skeleton, issue #11) was the first WP to run the canonical flow: /wp 3, a self-contained explainer with all seven questions in one message, the owner's answers recorded on 2026-10-03 before any code, then eight steps, each with one scoped commit and two lines in the step log. No step was marked known. The PR was reviewed, the explain-back and the Recap are written, and the PR is merged.

What went well

  • One canonical run. The decisions came first and were the owner's own (A1 Express, B2 ApiConfig, D1 pg, E1 Terminus body, F1 NodeSDK, G3 checked templates, I3 spike). Every later change was written down as an amendment under Decision instead of rewriting the answers.
  • A spike before code, 8 of 8 rows go. One day of throwaway code on spike/wp-3-nest12 tested Nest 12 with Vitest, nestjs-pino, RabbitMQ and Testcontainers, better-auth, MCP, OpenTelemetry, LangGraph and the install scripts. No library decided by an ADR failed. The one partial (Nest controller spans, blocked by a declared version range) took the fallback named in advance (S2). Two traps surfaced before any real code: Biome's import type fix breaks DI (S1, an override for Nest paths), and the OTel SDK starts exporters nobody asked for.
  • Nest 11 or 12, answered with evidence. When the owner asked whether to step back to Nest 11, the spike rows showed only one finding came from Nest 12, and it needed no code.

What changed

  • ADR-043. The step 3 code used an own config loader, while ADR-007 named @nestjs/config, and the explainer had not raised it. The owner kept the own loader (validation before NestFactory.create, one loader for the app and the OTel entry, typed ApiConfig), and ADR-043 supersedes ADR-007 on the library only. Lesson: before writing code, check it against the accepted ADRs, not only against the explainer.
  • The Docker context fix. Testcontainers does not read the Docker CLI context that OrbStack uses, so pnpm test:int failed where pnpm dev:up worked. The integration setup now asks docker context inspect and sets DOCKER_HOST.
  • The domain rule fix. Widening the dependency-cruiser rules to templates/ showed that domain-imports-only-domain only flagged imports into apps/, so a domain file could import @nestjs/common. It now flags any import outside the module's domain/. The same widening caught a template test that imported an adapter from application/.
  • The code map. An interactive map of the repo (docs/architecture/code-map.html) now lives in the repo and is updated as the last step of every WP (the new Map stage). Reviewing the design through it found real fixes, applied in their own commit.

After WP-3 the owner chose to run everything in Claude Code sessions from the repo; firstmate was tried for one fit check and not adopted.

Still open after the trials

  • ADR-010 on observability: the @nestjs/observe question is settled by WP-3 decision F1 (NodeSDK with an explicit list, no new ADR). The broker in api's readiness check is still questionable with an outbox; WP-5 decides.
  • The plan report names databases jadero_content; the code follows ADR-027's content_dev. The report should follow the ADR.
  • The Project views are a manual step.
