# Sessions: how to run a work package with Claude Code

Every work package runs in a Claude Code session started in this repo, in the cloud (claude.ai/code) or on the owner's machine. There is no other framework: the repo carries the whole flow (`AGENTS.md`, `CLAUDE.md`, `.claude/`). Decided 2026-10-04, after WP-1 and WP-3 ran this way; the owner's framework (firstmate) was tried for one fit check and not adopted. ADR-028 already chose repo-local tooling (option D) and left adopting the framework for later (option C); that door stays open but nothing here depends on it.

## What a new session reads

The session loads `CLAUDE.md` (which imports `AGENTS.md`) by itself, and the SessionStart hook prints the branch and the explainer status. For the WP at hand it reads, on demand: its row in `docs/plan/decisions.json` and `docs/plan/report.md` section 14, its GitHub issue, the ADRs it names, and `docs/learning/wp-N.md`. The flow in detail is `docs/agent-tooling.md`; the daily loop and the "When something blocks" table are `docs/local-playbook.md`; the code at a glance is `docs/architecture/code-map.html`.

## Cloud or local

| | Cloud session (claude.ai/code) | Local session (Claude Code on the owner's machine) |
|---|---|---|
| Good for | explainers, decisions, platform code, docs, reviews, publishing the artifacts | the same, plus anything that needs Docker |
| Docker (`pnpm dev:up`, `pnpm test:int`) | not available: the owner runs those steps locally and pastes the output | available (OrbStack works) |
| GitHub | through its GitHub tools; it cannot delete branches; PR bodies get a "Generated by Claude Code" footer to delete before the squash | `gh` |
| Node and pnpm | may need `export PATH=~/.local/node24/bin:$PATH` or a setup step | `nvm use && corepack enable` |
| Commit identity | set `git config user.name` and `user.email` to the owner in the checkout | already the owner |
| Security | runs in a sandbox, plus the repo's permission settings | no sandbox unless the owner sets one up: the protection is the `.env` deny in `.claude/settings.json`, the learning gate and the owner reviewing each step |
| Artifacts (code map, process pages) | can republish them | edits the repo files; the next cloud session republishes |

## Prompt: start a work package

Change the number, title and issue; the rest stays.

```
Next work package in jadero-dev: WP-5 (messaging foundation and the agent skeleton), issue #13, a
learning WP. Follow the repo's flow exactly (AGENTS.md section 5, docs/agent-tooling.md, docs/sessions.md):
1. git fetch origin, then pnpm install && pnpm verify:all on origin/main.
2. /wp 5: check that its dependencies are closed, create wp/5-<slug> from origin/main, propose 4 to 8
   steps and the definition of done from the issue, then stop.
3. After my go: /learn-step 5. Self-contained explainer; concepts labelled Own, Recognize or Delegate;
   for each decision the forces, at least three options (one you would not pick, and when it would
   win) and what would make it wrong; all questions in one message, recommendations in a separate block
   after the questions. I answer first with my pick and one risk, then we compare. Stop. No code under
   learning paths.
4. When I answer: record the decision (decision: recorded), then build one step at a time under the
   step contract (AGENTS.md section 5): files, explainer paragraph and ADR lines before writing (stop if
   the code would depart from an ADR), pnpm verify, show it running, privacy check, two step-log lines
   from the diff, one check question for me, one scoped commit. @agent-reviewer after about half the
   steps. Steps that need Docker: tell me the exact commands and wait for my output.
5. Last step: update docs/architecture/code-map.html (its JSON data) and the docs the WP changed.
6. Open the PR with Closes #13, run @agent-reviewer, fix its findings, then do my explain-back in
   interview form (why, what else, when to change it, what happens when it fails; I draw the main
   trace from memory) and write it in the Recap. I write the journal post. I merge.
Answer in Spanish; files in plain English, no em dashes, no attribution lines in commits or PRs.
```

## Prompt: resume a work package in a new session

```
Resume WP-N in jadero-dev on branch wp/N-<slug>. Read docs/learning/wp-N.md (Decision, Step log) and
git log origin/main..HEAD, tell me in three lines where we are and which step is next under the step
contract, then wait for my go.
```

## Prompt: a chore outside a work package

```
In jadero-dev, on a new branch chore/<slug> from origin/main: <what to change>. Keep it to that change,
pnpm verify green, one scoped commit, a PR without Closes, and tell me when it is ready. Do not add
commits to a PR after saying it is ready.
```

## Rules that keep a session on track

- A request for a report or a check changes nothing until the owner says go; then one PR per agreed change.
- Compact after the decision is recorded and after the review; keep branch, WP, explainer path, step list with done marks and open findings.
- One session per WP is enough when compacting at those two points; a new session resumes with the prompt above.
