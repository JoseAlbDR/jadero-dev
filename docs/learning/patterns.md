# Pattern catalog, indexed by symptom

At work a problem arrives as a ticket that describes a symptom, not a pattern name. This catalog goes the other way from the explainers: it starts from the symptom and leads to the pattern, its trade-off and where it lives in this repo. It is the source of the `/step` warm-up tickets (`AGENTS.md` section 5, "Warm-up as a ticket"), and `/wrap-wp` adds each WP's new patterns to it.

Columns: the symptom as a ticket would say it; the pattern; the trade-off and when an alternative wins; a generic example from the owner's work domain (supplier relationship management), or another domain where it fits better; where the pattern lives in this repo.

## Data and consistency

| Symptom | Pattern | Trade-off, when an alternative wins | Example | Where in this repo |
|---|---|---|---|---|
| Two people save the same record and one change silently disappears | Optimistic concurrency (version column, stale save rejected) | The loser reloads and redoes the edit. A pessimistic lock wins when collisions are frequent and edits short; last write wins when there is one editor; field merge when the fields are independent | Two reviewers edit the same supplier rating in an approval step | WP-12 D5, `apps/api` content module (version per document, `If-Match` over HTTP) |
| A save is half applied: the main row changed, the related rows did not | Unit of work (one transaction around the use case) | Holds locks for the whole use case. A saga wins when the steps span services or databases | A supplier rating is saved but its measures are not | WP-10 D6, `withTransaction` in `packages/platform-nest`, the module template |
| The record changed but the other service never heard about it, or heard about a change that was rolled back | Transactional outbox plus relay | One more table and a relay process. Publishing after commit wins when losing an event now and then is acceptable; change data capture wins at high volume | A supplier is approved, the contracts side never gets the event | WP-5, `packages/messaging` (outbox, relay), used by `api` and `api-worker` |
| A consumer handles the same message twice: duplicate mails or rows | Idempotent consumer (inbox of processed message ids) | One lookup per message. A naturally idempotent effect (an upsert, setting a state) needs no inbox | An information request reminder goes to a supplier twice | WP-5, `packages/messaging` inbox; the `agent` consumer |
| Two worker instances pick up the same job | Atomic claim (`FOR UPDATE SKIP LOCKED`) | Needs a database that supports it. A single worker or a leader wins when strict order matters | Two workers both start the AI analysis of the same contract | WP-5, the outbox relay in `packages/messaging` |
| One bad message fails forever and blocks or floods the logs | Retry with backoff plus dead-letter queue | Delays real failures by the backoff. Dropping with a log wins when the message has no value later | A corrupt certificate PDF fails the document analysis on every retry | WP-5, `packages/messaging/src/topology` (TTL retry queues, DLX) |
| Renaming a field or event broke the other service during the deploy | Expand/contract (parallel change) | Two releases instead of one. A single change wins when one deploy unit owns both sides | A rating field consumed by a reporting service is renamed | WP-5 versioned events in `packages/contracts`; WP-10 D3 migrations |
| A service broke because another changed its tables | Database per service, read model fed by events | Data is eventually consistent and copied. A shared schema is fine inside one monolith | A contracts module reads the supplier tables directly | WP-10 D4, ADR-029; one database and role per service in `infra/` |
| Auditors ask who changed a document and want the old version back | Append-only history with a current-version pointer | More rows, reads go through the pointer. Update in place plus an audit log wins when history is rarely read | Contract clauses need every past version and a rollback | WP-12 D2, revisions in the `apps/api` content module |
| A record reaches an impossible state (approved without a reviewer, published without a translation) | Finite state machine with transition guards | Every new state needs its transitions. Independent flags win when the states really are independent | An approval step marked done while a condition is still open | WP-12 D4, publish and approval in the content domain |
| Content was changed after it was approved, and the approval still counts | Approval bound to a revision | Every change needs a new approval. Resetting a flag on save wins when there is no history | A supplier certificate replaced after the reviewer approved it | WP-12 D4, knowledge entry approval in the content module |
| Private fields show up in a public API response | Defense in depth (not selected, and stripped by the response schema) | Two places to keep in sync. One layer is enough only for data that is not sensitive | Internal supplier notes leak into a supplier portal response | WP-12, the public read API of the content module |

## Service edges and operations

| Symptom | Pattern | Trade-off, when an alternative wins | Example | Where in this repo |
|---|---|---|---|---|
| The same unchanged data is downloaded again and again, pages are slow | HTTP conditional request (ETag, 304) plus `Cache-Control` | Stale for the freshness window. Push invalidation wins when a change must show at once | A supplier profile page refetches the full profile on every visit | WP-12 D6, `/v1/content`; WP-16 pages in `apps/web` |
| Users still see the old version after a publish | Tag-based invalidation | Each write must know its tags. A short time to live wins when some staleness is fine | A published assessment template still shows the old questions | WP-12 D6, `revalidateTag` in `apps/web` |
| Nobody can tell which request caused an error across services | Correlation id and trace context propagation | Every hop must carry the headers. Plain per-service logs do for a single service | A failed approval notification cannot be tied to the user action | WP-3 logging in `packages/platform-nest`; WP-5 trace context in message headers |
| An error page shows a stack trace or SQL to the user | Problem details with exception shielding (global handler) | Detail lives in the logs only. Full detail is fine in local development | A supplier portal error shows the failing query | WP-3 and ADR-047, the error handler in `packages/platform-nest` |
| Invalid input crashes deep inside the code | Schema validation at the boundary | One schema per boundary. Internal calls between trusted modules skip it | A supplier upload with a missing tax field fails in the rating job | WP-3; Zod schemas in `packages/contracts` |
| A service starts with a missing setting and fails hours later | Fail fast with typed configuration | Boot refuses to start. Lazy defaults win only for optional features | The AI analysis key is missing and the first contract upload fails | WP-3, `loadConfig` in `packages/platform-nest` |
| A deploy cuts requests or messages in flight | Graceful shutdown and connection draining | Deploys take a little longer. An instant kill is fine for stateless jobs that are retried | A rating save is cut off during a rollout | WP-3, shutdown hooks in `packages/platform-nest` |
| Traffic reaches an instance whose database is down | Liveness versus readiness probes | Checks must stay cheap and bounded. One health check does for a single process without dependencies | Requests fail while a service waits for its database after a restart | WP-3, the health module in `packages/platform-nest` |
| The tests pass on the fake, production breaks on the real adapter | Contract test suite run against fake and real adapter | Two adapters to keep under one suite. Integration tests alone win when there is no fake | An in-memory supplier repository sorts differently from the SQL one | WP-5 `MessageBus`; WP-10 repository contract in `templates/nest-module/` |
| Business rules cannot be tested without a database | Repository port and adapters (dependency inversion) | One more interface per aggregate. Calling the ORM directly is fine in a trivial layered module | Rating rules testable only against Postgres | WP-10 D5, the hexagonal shape in `templates/nest-module/` |

## Delivery and supply chain

| Symptom | Pattern | Trade-off, when an alternative wins | Example | Where in this repo |
|---|---|---|---|---|
| CI runs everything for a one-line change and takes too long | Affected builds plus a content-addressed cache | Inputs must be declared or the cache lies. A full run wins as a periodic backstop | A docs change waits on the whole test suite | WP-1 and WP-6 D2, Turborepo in `turbo.json` and `.github/workflows/` |
| A required check was skipped and the PR merged as if it passed | Fail safe versus fail open (skipped means success) | Checks must always report. A path filter is fine only on a check that is not required | A security scan skipped on a workflow change | WP-6 D10, the required checks in `.github/workflows/` |
| A key was committed to the repository | Secret scanning, rotate before rewriting history | Rotation is the fix, a rewrite only cleans up. Push protection catches it before the commit lands | An AI provider key in a test fixture | WP-6 D7, the `secrets` job in `.github/workflows/` |
| A dependency update pulled in a compromised release | Cooldown period on updates | Updates arrive days later. An immediate update wins for a known security fix | A new parser release with malware installs the same day | WP-6 D9, Renovate in `renovate.json` |
| The team ignores the alerts because there are too many | Diff-based gate and ratchet | Old problems stay until someone fixes them. A full-state gate wins on a new repository | Every PR shows the same 40 old warnings | WP-6 Q2 and D5, the coverage gates and vulnerability checks in CI |
