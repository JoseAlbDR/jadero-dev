# Pattern catalog, indexed by symptom

At work a problem arrives as a ticket that describes a symptom, not a pattern name. This catalog goes the other way from the explainers: it starts from the symptom and leads to the pattern, its trade-off and where it lives in this repo. It is the source of the `/step` warm-up tickets (`AGENTS.md` section 5, "Warm-up as a ticket"), and `/wrap-wp` adds each WP's new patterns to it.

Columns: the symptom as a ticket would say it; the pattern; the trade-off and when an alternative wins; a generic example from the owner's work domain (supplier relationship management), or another domain where it fits better; where the pattern lives in this repo.

## Data and consistency

| Symptom | Pattern | Trade-off, when an alternative wins | Example | Where in this repo |
|---|---|---|---|---|
| Two people save the same record and one change silently disappears | Optimistic concurrency (version column, stale save rejected) | The loser reloads and redoes the edit. A pessimistic lock wins when collisions are frequent and edits short; last write wins when there is one editor; field merge when the fields are independent | Two reviewers edit the same supplier rating in an approval step | WP-12 D5, `apps/api` content module (version per document, `If-Match` over HTTP) |
| A save is half applied: the main row changed, the related rows did not | Unit of work (one transaction around the use case) | Holds locks for the whole use case. A saga wins when the steps span services or databases | A supplier rating is saved but its measures are not | WP-10 D6, `withTransaction` in `packages/platform-nest`, the module template |
| The record changed but the other service never heard about it, or heard about a change that was rolled back | Transactional outbox plus relay | One more table and a relay process. Publishing after commit wins when losing an event now and then is acceptable; change data capture wins at high volume | A supplier is approved, the contracts side never gets the event | WP-5, `packages/messaging` (outbox, relay), used by `api` and `api-worker` |
| A consumer handles the same message twice: duplicate mails or rows | Idempotent consumer (inbox of processed message ids) | One lookup per message. A naturally idempotent effect (an upsert, setting a state) needs no inbox | An information request reminder goes to a supplier twice | WP-5, `packages/messaging` inbox; the `agent` consumer |
| Two worker instances pick up the same job | Atomic claim (`FOR UPDATE SKIP LOCKED`) | Needs a database that supports it. A single worker or a leader wins when strict order matters | Two workers both start the AI analysis of the same contract | WP-5, the outbox relay in `packages/messaging` |
| One bad message fails forever and blocks or floods the logs | Retry with backoff plus dead-letter queue | Delays real failures by the backoff. Dropping with a log wins when the message has no value later | A corrupt certificate PDF fails the document analysis on every retry | WP-5, `packages/messaging/src/topology` (TTL retry queues, DLX) |
| Renaming a field or event broke the other service during the deploy | Expand/contract (parallel change) | Two releases instead of one. A single change wins when one deploy unit owns both sides | A rating field consumed by a reporting service is renamed | WP-5 versioned events in `packages/contracts`; WP-10 D3 migrations; WP-9 D5 and D6, expand-only schema, configuration and topology so a rollback to N-1 works |
| A service broke because another changed its tables | Database per service, read model fed by events | Data is eventually consistent and copied. A shared schema is fine inside one monolith | A contracts module reads the supplier tables directly | WP-10 D4, ADR-029; one database and role per service in `infra/` |
| Auditors ask who changed a document and want the old version back | Append-only history with a current-version pointer | More rows, reads go through the pointer. Update in place plus an audit log wins when history is rarely read | Contract clauses need every past version and a rollback | WP-12 D2, revisions in the `apps/api` content module |
| A record reaches an impossible state (approved without a reviewer, published without a translation) | Finite state machine with transition guards | Every new state needs its transitions. Independent flags win when the states really are independent | An approval step marked done while a condition is still open | WP-12 D4, publish and approval in the content domain; WP-9 D1, the deploy states in `infra/scripts/deploy.sh` |
| Content was changed after it was approved, and the approval still counts | Approval bound to a revision | Every change needs a new approval. Resetting a flag on save wins when there is no history | A supplier certificate replaced after the reviewer approved it | WP-12 D4, knowledge entry approval in the content module |
| Private fields show up in a public API response | Defense in depth (not selected, and stripped by the response schema) | Two places to keep in sync. One layer is enough only for data that is not sensitive | Internal supplier notes leak into a supplier portal response | WP-12, the public read API of the content module; WP-8 D1, D3, D4 (cloud firewall plus `127.0.0.1` binds, key restrictions plus a re-validating root script, `pg_hba.conf` plus `REVOKE CONNECT`) in `infra/` |
| After a restore, one service is missing records another service believes it already sent | Point-in-time consistent restore (every database from the same complete run, a run marker) | A failed item sends everyone back one more run. Continuous archiving (WAL) wins when the loss window must be minutes; a periodic full snapshot event is the backstop for what still drifts | The supplier service restored to Tuesday, the document analysis service to Monday: Tuesday's approved-supplier events are marked sent and never arrive | WP-8 D7, the `backup-run.complete` marker in `infra/scripts/backup.sh` and `infra/scripts/restore.sh`; WP-14 `knowledge.snapshot.v1` |

## Service edges and operations

| Symptom | Pattern | Trade-off, when an alternative wins | Example | Where in this repo |
|---|---|---|---|---|
| The same unchanged data is downloaded again and again, pages are slow | HTTP conditional request (ETag, 304) plus `Cache-Control` | Stale for the freshness window. Push invalidation wins when a change must show at once | A supplier profile page refetches the full profile on every visit | WP-12 D6, `/v1/content`; WP-16 pages in `apps/web` |
| Users still see the old version after a publish | Tag-based invalidation | Each write must know its tags. A short time to live wins when some staleness is fine | A published assessment template still shows the old questions | WP-12 D6, `revalidateTag` in `apps/web` |
| Nobody can tell which request caused an error across services | Correlation id and trace context propagation | Every hop must carry the headers. Plain per-service logs do for a single service | A failed approval notification cannot be tied to the user action | WP-3 logging in `packages/platform-nest`; WP-5 trace context in message headers |
| An error page shows a stack trace or SQL to the user | Problem details with exception shielding (global handler) | Detail lives in the logs only. Full detail is fine in local development | A supplier portal error shows the failing query | WP-3 and ADR-047, the error handler in `packages/platform-nest` |
| Invalid input crashes deep inside the code | Schema validation at the boundary | One schema per boundary. Internal calls between trusted modules skip it | A supplier upload with a missing tax field fails in the rating job | WP-3; Zod schemas in `packages/contracts` |
| A service starts with a missing setting and fails hours later | Fail fast with typed configuration | Boot refuses to start. Lazy defaults win only for optional features | The AI analysis key is missing and the first contract upload fails | WP-3, `loadConfig` in `packages/platform-nest` |
| A deploy cuts requests or messages in flight | Graceful shutdown and connection draining | Deploys take a little longer. An instant kill is fine for stateless jobs that are retried | A rating save is cut off during a rollout | WP-3, shutdown hooks in `packages/platform-nest` |
| Traffic reaches an instance whose database is down | Liveness versus readiness probes | Checks must stay cheap and bounded. One health check does for a single process without dependencies | Requests fail while a service waits for its database after a restart | WP-3, the health module in `packages/platform-nest` |
| The tests pass on the fake, production breaks on the real adapter | Contract test suite run against fake and real adapter | Two adapters to keep under one suite. Integration tests alone win when there is no fake | An in-memory supplier repository sorts differently from the SQL one | WP-5 `MessageBus`; WP-10 repository contract in `templates/nest-module/` |
| Business rules cannot be tested without a database | Repository port and adapters (dependency inversion) | One more interface per aggregate. Calling the ORM directly is fine in a trivial layered module | Rating rules testable only against Postgres | WP-10 D5, the hexagonal shape in `templates/nest-module/` |
| A nightly job stopped weeks ago and nobody noticed | Dead man's switch (heartbeat on success, alert on silence) | The alert lags by the interval. An alert on failure is faster but stays silent when the job never starts; a probe wins for a service that is always up | The nightly reminder for expiring supplier certificates died in a migration and sent nothing | WP-8 D7 and D8, the push heartbeat in `infra/scripts/backup.sh` to an Uptime Kuma push monitor; WP-9 step 6d, the Kuma email notification that the heartbeat lacked (`docs/runbooks/deploy.md`) |
| The whole server went down at night and no alert came | Monitoring by failure domain (an outside probe that also watches the watcher) | The outside probe sees only the public edge, never the private health endpoints or the broker, so it pairs with the monitor inside. One monitor is enough only when it cannot fail together with what it watches, such as a managed platform's own alerting | The supplier portal's health checks run on the same cluster they watch, and the cluster outage stays silent | WP-9 D9, UptimeRobot on `new.jadero.dev` and on the Uptime Kuma status page, `docs/runbooks/deploy.md`; from WP-8 D8 |
| We have backups, but nobody knows whether they restore or how long it takes | Restore drill as the acceptance test (measured RTO) | Time spent once per release. A managed database with provider-tested point-in-time recovery wins when there is budget, and the drill still covers what lives outside it | Contracts and their AI analysis results are backed up nightly, never restored | WP-8 D7, `infra/scripts/restore.sh` and `docs/runbooks/restore.md` (ADR-050) |
| An integration key leaked and it can do everything an admin can | Least privilege with a capability-scoped credential (forced command, re-validated on the privileged side) | Every new use needs a new scope. A broad key is tolerable only when the system holds nothing of value | The key an ERP import uses to update suppliers can also delete contracts | WP-8 D3, `infra/scripts/deploy-entry` and the `deploy` user's key line |
| An audit finding asks why internal traffic is not encrypted | Accepted risk with compensating controls and revisit triggers | The risk stays and must be revisited. Encrypting the hop wins once traffic crosses a host or a network you do not own | Unencrypted calls between the supplier service and its database on one private network | WP-8 Q1, ADR-050; ADR-052 for client addresses in the edge error logs |
| A privacy review flags full IP addresses and query strings in the logs | Data minimization in logs (network part only, no query string, short retention) | Less detail for abuse cases. A keyed hash wins when unique visitors must be counted; full detail for a short time wins during an active attack | Supplier portal logs keep each contact's address and search terms for months | WP-8 step 5, the `jadero` log format in `infra/nginx/nginx.conf`, `infra/logrotate/jadero-nginx` (ADR-052) |
| A switch to a new access path or a new password locked people or services out | Make before break (open and prove the new path, then close the old; keep a break-glass) | Both paths live for a while. A hard cut wins only when the old path is compromised | Moving supplier portal sign-in to a new identity provider cuts off users mid-session | WP-8 step 2 (SSH over Tailscale before the public rule closed), step 4a (password rotation order), `docs/runbooks/server-access.md` |
| After recreating the container, the broker or database came up empty though the volume is still there | Stable identity for stateful workloads (fixed node name) | The name must never change by accident. A stateless service needs none | The queue broker behind document analysis is recreated with a new host name and its pending jobs seem gone | WP-8 step 4c, the fixed RabbitMQ host name in `infra/compose/compose.ops.yml` |

## Delivery and supply chain

| Symptom | Pattern | Trade-off, when an alternative wins | Example | Where in this repo |
|---|---|---|---|---|
| CI runs everything for a one-line change and takes too long | Affected builds plus a content-addressed cache | Inputs must be declared or the cache lies. A full run wins as a periodic backstop | A docs change waits on the whole test suite | WP-1 and WP-6 D2, Turborepo in `turbo.json` and `.github/workflows/` |
| A required check was skipped and the PR merged as if it passed | Fail safe versus fail open (skipped means success) | Checks must always report. A path filter is fine only on a check that is not required | A security scan skipped on a workflow change | WP-6 D10, the required checks in `.github/workflows/` |
| A key was committed to the repository | Secret scanning, rotate before rewriting history | Rotation is the fix, a rewrite only cleans up. Push protection catches it before the commit lands | An AI provider key in a test fixture | WP-6 D7, the `secrets` job in `.github/workflows/` |
| A dependency update pulled in a compromised release | Cooldown period on updates | Updates arrive days later. An immediate update wins for a known security fix | A new parser release with malware installs the same day | WP-6 D9, Renovate in `renovate.json` |
| The team ignores the alerts because there are too many | Diff-based gate and ratchet | Old problems stay until someone fixes them. A full-state gate wins on a new repository | Every PR shows the same 40 old warnings | WP-6 Q2 and D5, the coverage gates and vulnerability checks in CI |
| Staging and production drifted: a permission removed by hand never came back, a new role is missing on the live database | Convergent provisioning (desired state, re-run on every deploy) | The script must be safe to re-run, and an additive apply leaves orphans, so removal stays a deliberate step that the script reports. A create-once init is fine for throwaway environments | Reviewer roles of an approval flow configured by hand per environment differ between test and live | WP-8 D4, `infra/postgres/provision.sql` and `infra/rabbitmq/provision-users.sh` (with the orphan queue warning) |
| A configuration change opened an internal port or widened access, and it was found only on the server | Policy as code with tests (shift-left guardrail, fitness function) | Each rule needs a test kept up to date. A manual review is enough for a rule that changes once a year | A config change exposes the document analysis service's admin port | WP-8, `scripts/compose-hardening.mjs`, `scripts/nginx-hardening.mjs` and the Tailscale policy `tests`; from WP-7 |
| A deploy died half way and nobody knows what it changed, so a rerun either repeats a step or skips one | State machine with a write-ahead journal and a point of no return | One write per state and a recovery rule per zone (before the point of no return throw the run away, after it compensate). One transaction wins when every step sits in one database; a workflow engine (Temporal, Step Functions) wins with many long flows | The AI analysis of a contract extracts clauses, saves them and notifies the reviewers; the worker dies after saving and the rerun saves them twice or never notifies | WP-9 D1, the journal, state and lock in `infra/scripts/deploy.sh`, `docs/runbooks/deploy.md` |
| A failed release left the database migrated, and going back needs a down migration nobody trusts | Compensating rollback to N-1 on shared state that only moves forward (roll the code back, never the schema) | Every breaking change takes two releases, and a rollback goes back one release only. A down migration wins when no other release reads the data yet; a restore from backup wins when the data itself is wrong | A release adds a field to supplier information requests; the rollback runs the previous release, which must still read the new rows | WP-9 D1, D4 and D5, `roll_back` in `infra/scripts/deploy.sh`, the step 6c rotation drill |
| Production runs a build that staging never tested: the image behind a tag changed between the test and the release | Build once, deploy many, promotion by digest (immutable reference instead of a movable tag) | The digest has to travel from the build to every environment and be checked where it is pulled. Rebuilding per environment wins only when the environments really need different binaries, which configuration should avoid | A certificate parsing service is validated in staging, and the production deploy pulls `latest` and gets a newer build | WP-9 D8, the `digests` job in `.github/workflows/release.yml`, `deploy.yml` and the digest check in `infra/scripts/deploy.sh`; from WP-7 D7 |
| A staging credential could also deploy to production, or a branch job could reach a protected environment | Environment-bound credentials (one key and identity per environment, the binding checked on the server side) | More keys and identities to rotate and set up. One shared credential is fine only with a single environment | An integration token issued for a supplier's test tenant also accepts calls on the production tenant | WP-9 D2, the environment in each key line read by `infra/scripts/deploy-entry`, the two Tailscale federated identities with exact subjects, GitHub environment secrets |
| After a rollback, messages go to the dead-letter queue sooner than configured, and no error shows anywhere | Forward-only guard on shared configuration with a write-ahead record (record the version before applying, apply only an equal or newer one) | A deliberate downgrade needs a manual step. A declarative tool that owns the whole topology and deletes what it does not declare (Terraform style reconciliation) wins when one owner applies everything | Two services share the approval flow configuration, and an older release re-imports the old steps and conditions | WP-9 Q2 and ADR-053, `apply_topology` and `MESSAGING_VERSION` in `infra/scripts/deploy.sh`, `topology-import.int.test.ts` |
