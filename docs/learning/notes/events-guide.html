Section 1

Mental model

Message, event, command

A message is any bytes a producer hands to a broker for someone else to read. Two kinds matter, and they differ in who decides what happens next.

Event: a fact, past tense

"This happened." The producer does not know or care who listens. Zero, one or five consumers may react. In this repo: system.ping.v1, and planned ones like content.published.v1 and contact.received.v1 (ADR-029 rule 2).

Command: a request, imperative

"Please do this." It has one intended handler, and the sender expects it to be done. ADR-029 plans commands only for admin actions, such as knowledge.reindex.requested.v1. Note how even that is named like a fact ("was requested"), which keeps it routable like any event.

The test at work: if the producer would be surprised that nobody reacted, it is a command. If it would not care, it is an event.

Producer, broker, consumer

The producer writes the message. The broker (RabbitMQ here) receives it on an exchange, which is a router with no storage, and copies it into every queue whose binding matches. The queue stores the message until a consumer takes it and acks it. If you know EventBridge: the exchange plays the event bus, a binding plays a rule with its pattern, and the queue plays the SQS target.

Why asynchronous between services here

Two rules in AGENTS.md section 4 force it:

  • Rule 2. Between api, agent and contact, only asynchronous messages through the outbox and RabbitMQ. Synchronous HTTP only at the edge.
  • Rule 3. A service that needs another's data keeps its own read model fed by events; the agent never calls api.

The reason is failure isolation. If agent called api over HTTP on every chat message, an api outage would take chat down too, and two services that cannot run without each other are a distributed monolith. With events, api can be down for an hour: agent keeps answering from its own copy, which is a little stale. That trade, availability for a few seconds of staleness, is called eventual consistency, and the pattern of copying the data a service needs into its own store is event-carried state transfer.

    The same matching rules are coded in packages/messaging/src/topic.ts (topicMatches) so the in-memory bus used in unit tests routes exactly like the broker. This repo binds one exact key per contract version rather than wildcards, so a v2 never reaches a consumer that only understands v1.

    Three queue types

    TypeWhat it isWins when
    quorumreplicated with the Raft consensus algorithm, durable, tracks a delivery count per messagethe message must not be lost; the default for anything that matters
    classicthe original single-node queuetemporary, non-critical queues (reply queues, caches)
    streaman append-only log; consumers read from an offset and nothing is deleted on ackreplay, many readers of the same history, Kafka-like use

    Every queue here is quorum. On a single node there is no replication to gain, but quorum queues bring the delivery limit that stops poison messages, and the topology stays the same if the broker ever gets more nodes.

    Declared arguments versus policies

    A queue's arguments are fixed when it is declared: RabbitMQ refuses to change them later, so changing a TTL would mean deleting the queue and its messages. A policy is a rule matched by name pattern that the broker applies, and re-applies at once when it changes. So buildDefinitions (packages/messaging/src/topology/definitions.ts) declares only x-queue-type: quorum, and everything tunable is a policy:

    // policy "agent.system.ping", pattern ^agent\.system\.ping$
{ "dead-letter-strategy": "at-least-once", "overflow": "reject-publish",
  "dead-letter-exchange": "jadero.dlx", "dead-letter-routing-key": "agent.system.ping",
  "delivery-limit": 20 }
// policy "agent.system.ping.retry.1m"
{ ..., "message-ttl": 60000, "dead-letter-exchange": "agent.retry",
  "dead-letter-routing-key": "agent.system.ping" }

    ADR-054One shared direct exchange, jadero.dlx, routes each consumer queue's dead letters to its <queue>.dlq.

    Topology as code, and no configure right least privilege

    The topology lives in one place, packages/messaging/src/topology/. pnpm --filter @jadero/messaging topology runs scripts/write-definitions.mjs, which writes infra/rabbitmq/definitions.json (dev, with fixed dev passwords), infra/rabbitmq/server/definitions/prod.json and staging.json (no users), and infra/rabbitmq/server/permissions.tsv, which provision-users.sh applies with passwords from the environment. A test fails while the generated files are stale.

    The adapter declares nothing. Service users get configure: ^$, so they cannot create, change or delete an exchange or queue. A buggy deploy cannot quietly redefine the topology; only the reviewed definitions can. The rights, from buildPermissions:

    Userconfigurewriteread
    api_prod^$^(jadero\.events)$^$
    agent_prod^$^(agent\.retry)$^(agent\.system\.ping)$
    ops_admin.*.*.*

    One virtual host per environment

    A vhost is a namespace inside one broker: its own exchanges, queues and permissions. Dev uses dev; the server's one RabbitMQ serves /prod and /staging. User names are global, so they carry the environment (agent_staging), and a staging user has no rights on /prod. It is the same idea as one AWS account per environment, at a fraction of the cost.

    Section 4

    Delivery semantics

    GuaranteeHow you get itWhat breaks
    at-most-onceack before processing, or fire and forgeta crash loses the message
    at-least-onceack after processing; publish again until confirmedduplicates: a crash between work and ack redelivers
    effectively-onceat-least-once plus an idempotent consumeronly effects outside the transaction (an email, an external API call)

    True exactly-once delivery across a network is not available: the sender can never tell "lost" from "slow". What you can build is exactly-once effect. This repo has duplicates at two points by design: the relay's crash window between confirm and commit, and the consumer's crash window between commit and ack. The inbox covers both, because the dedupe row commits in the same transaction as the effect.

    The inbox only protects effects inside the consumer's own database transaction. If a handler sends an email, a duplicate sends a second email. The fix there is an idempotency key sent to the provider, or recording "sent" before sending and accepting a rare miss: you choose which failure you prefer.

    Ordering

    A single queue with a single consumer and prefetch 1 delivers in order. Every one of these breaks it: prefetch above 1 with async handlers, two or more consumers, a retry (the message comes back 10 s later behind newer ones), and the relay itself if several relays ran. So design consumers to not need order: carry a timestamp or version and ignore older ones, which is exactly the heartbeat's WHERE last_seen_at < excluded.last_seen_at guard. When order truly matters per entity, partition by key (Kafka partitions, SQS FIFO message groups, RabbitMQ single active consumer or a consistent hash exchange).

    Poison messages

    A message that can never succeed. Three guards here: validation in dispatch sends bad payloads to the DLQ at once, the retry tiers cap a throwing handler at four attempts, and the delivery limit catches messages that crash the process.

    Prefetch and backpressure backpressure

    Prefetch is how many unacked messages the broker pushes to one consumer before waiting. Too high: one slow pod hoards messages others could take, and memory grows. Too low: the consumer idles between round trips. Here it is sized from a downstream limit: prefetch 4 against a pool of 6 connections, so a burst of pings waits in the queue, which is durable and cheap, instead of failing on an exhausted pool. That is backpressure: the slow part sets the pace and the queue absorbs the rest. ADR-054 keeps 10 as the default in the adapter.

    ADR-054Prefetch is set per consumer, below its database pool: agent 4 against a pool of 6; the adapter default is 10.

    Peculiarities to remember

    • RabbitMQ pushes to consumers and forgets on ack. Rich routing in the broker; history is gone unless you use streams. An unroutable message is dropped unless you add an alternate exchange or mandatory publishing.
    • EventBridge + SNS + SQS is managed and pay-per-use, all at-least-once. Routing on payload fields is its strength. Every hop has its own retry and DLQ settings, so a failure can hide at the rule target, the SNS subscription or the SQS queue: check all three. The routing table you know at work (an event store forwarding to SNS topics) is the same exchange-binding-queue idea built from three services.
    • Kafka is a log, not a queue: consumers track an offset, many groups read the same history independently, and replay is free. Parallelism is capped by partition count, and one slow message blocks its partition, which is why retry topics exist.
    • NATS JetStream is small and fast, with subjects as a light routing model and both queue-like and log-like retention. Fewer built-in failure topologies than RabbitMQ; ADR-029 rejected it here because Nest's built-in NATS transport is fire and forget and the learning transfers less.

    Section 7

    Event sourcing and CQRS

    Event sourcing stores every change as an immutable event and treats them as the source of truth. Current state is not stored; it is derived by folding the events in order. CQRS (command query responsibility segregation) splits the write model from read models: writes append events, and projections turn them into tables shaped for each query.

    Worked example: a supplier rating

    A supplier's rating comes from assessments. Instead of a supplier_rating row with a score that gets overwritten, store the stream for supplier S-17. The fold is a pure function, state = events.reduce(apply, empty), with equal weights by default. Move the date: the page folds only the events with at <= that date.

      deliveryqualityweightsrating

      "What was S-17's rating on 2026-06-30?" Fold only the events with at <= 2026-06-30: 3.6. A table that stores only the final 4.4 cannot answer that, and an auditor asking why a supplier was blocked in June needs exactly that answer. That is the real reason to choose event sourcing: the history is the product.

      • Projections. A consumer folds events into supplier_rating_current for the list page, another into supplier_rating_monthly for a chart. Both can be dropped and rebuilt from the stream.
      • Snapshots. A supplier with 30,000 events is slow to fold, so store the state every N events (say at seq 1000) and fold only what came after.
      • Upcasting. Events are never edited. When v2 changes scores from 1 to 5 into 0 to 100, an upcaster converts v1 to v2 in memory while reading (score * 20), so the fold only knows the newest shape.
      • The cost. Every read model is eventually consistent; schema changes need upcasters forever; a wrong event cannot be deleted, only compensated by a new one; deleting personal data needs crypto-shredding or stream rewriting; and the team must think in events. For most CRUD it is a large tax for history nobody asks for.

      The outbox is not event sourcing

      Transactional outbox (this repo)

      State lives in normal tables and is the source of truth. The outbox row is a delivery buffer: it exists to get a message to the broker, and published rows are deleted after 7 days. Losing the outbox history loses nothing important.

      Event sourcing

      The event store is the state. Nothing is ever deleted; tables are disposable projections. Losing the events loses the business.

      They combine well: an event-sourced service still needs a reliable way to publish, and its event store often doubles as the outbox.

      How it could apply here, and what the repo does instead

      • The agent's usage and budget ledger (ADR-021, planned): every model response priced and summed into usage.llm_usage, with a daily cap. Append-only usage rows already look like events; full event sourcing would add projections of spend per day for a cap that resets daily. Overkill: the plan sums rows.
      • Content revisions (WP-12): each localized type has a *_revisions table of immutable jsonb documents, and a *_translations row with pointers to the latest and the published revision. That keeps full history and can show any past version, but each revision is a full snapshot, not a delta event, and the pointers are mutable state. It is versioned snapshots, the cheaper cousin of event sourcing.
      • The agent's search index (D-42): a CQRS read model in the sense that matters, derived from api's content and rebuildable from events. CQRS without event sourcing is common and cheap; this is that.

      Section 8

      Choreography and orchestration

      A business process that spans services cannot use one database transaction. A saga is the sequence of local transactions, each with a compensating action that undoes it if a later step fails.

      Choreography choreography

      No coordinator. Each service reacts to events and emits its own. content.published.v1 makes agent reindex and api-worker rebuild the PDF; neither knows about the other. Wins with few steps and independent reactions, which is this repo. Loses when the flow grows: nobody can see the whole process, and cycles creep in.

      Orchestration orchestrated saga

      One orchestrator holds the state of the process and sends commands: "verify certificate", then "update supplier status", then "notify", compensating on failure. Wins with many ordered steps, timeouts, human approvals and the need to answer "where is request 812 stuck?". Tools: a state table with a process manager, or a workflow engine (Step Functions, Temporal).

      A configurable approval flow, where a change passes steps with conditions and assigned reviewers, is orchestration by nature: the order and the waiting are the business.

      Self-check

      Eight questions

      Each carries what you need. Answer before opening.

      1. The relay publishes row R, the broker confirms, and the worker is killed before COMMIT. What happens to R, and who absorbs the effect?

      The claim's transaction rolls back, so published_at stays null and the row lock is released. The next poll claims R and publishes it again: the consumer receives the same envelope id twice. The inbox's (consumer, event_id) primary key turns the second delivery into a no-op. At-least-once publishing plus an idempotent consumer.

      2. A handler throws on every attempt. How many times does it run, and over roughly how long, before the message stops?

      Four runs: the first, then after 10 s, 1 min and 10 min. After the fourth throw, dispose finds no tier left and dead-letters it to agent.system.ping.dlq with "retries exhausted after 4 attempts". About 11 minutes plus processing time.

      3. Why does a retry go through agent.retry with an exact key, instead of being republished to jadero.events?

      Publishing to the topic exchange would route the copy to every queue bound to that event, so other services would run their handlers again. The per-service direct exchange and the wait queue's dead-letter routing key send it back to the one queue whose handler failed.

      4. You need the retry delay changed from 1 min to 2 min in production. What do you change, and why does nobody need to delete a queue?

      The tier in DEFAULT_RETRY_TIERS_MS, then regenerate the definitions. The delay is a policy (message-ttl), not a declared argument, and the broker applies a changed policy at once. Note the wait queue's name contains the delay label (.retry.2m), so a new tier means a new wait queue; the alternate exchange on agent.retry keeps any copy sent while the adapter and topology are out of step.

      5. A consumer process dies with an out-of-memory error on one specific message, every time. What stops the crash loop?

      The handler never returns, so the retry tiers never apply. The quorum queue counts each redelivery; the policy's delivery-limit: 20 makes the broker dead-letter the message through jadero.dlx to agent.system.ping.dlq, and the pod recovers.

      6. An online shop: an order-paid event must update stock, send a receipt email, and notify the warehouse. One service, one queue, or one queue per reaction?

      One queue per reaction (fan-out). Each has its own failure: the email provider down must not block stock or the warehouse, and each needs its own retries and DLQ. Stock can be idempotent with an inbox; the email needs an idempotency key with the provider, because it is an effect outside the database.

      7. You scale the agent consumer to three pods. The heartbeat table still ends up right. Why, even though order is lost?

      The upsert only writes when the stored last_seen_at is older than the incoming one. Whatever order the three pods finish in, the newest ping wins. Commutative, last-writer-wins updates make ordering irrelevant for this effect.

      8. A booking platform wants to show what a hotel's cancellation policy was on the day a guest booked. Is the outbox enough, and what is the cheapest design that works?

      No: outbox rows are deleted after delivery and are not the source of truth. Full event sourcing would work but is costly. The cheapest fit is versioned snapshots, like this repo's content revisions: keep every policy version with its validity time, and store the version id on the booking.
