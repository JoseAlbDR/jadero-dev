Events Field Guide

Event-driven design as this repo builds it, traced through one real event, system.ping.v1, from a Postgres row in api to a Postgres row in agent. Every name below is a real name from the code.

messaging.outbox→OutboxRelay→jadero.events→agent.system.ping→HeartbeatConsumer→messaging.inbox

Section 1

Mental model

Message, event, command

A message is any bytes a producer hands to a broker for someone else to read. Two kinds matter, and they differ in who decides what happens next.

Event: a fact, past tense

"This happened." The producer does not know or care who listens. Zero, one or five consumers may react. In this repo: system.ping.v1, and planned ones like content.published.v1 and contact.received.v1 (ADR-029 rule 2).

Command: a request, imperative

"Please do this." It has one intended handler, and the sender expects it to be done. ADR-029 plans commands only for admin actions, such as knowledge.reindex.requested.v1. Note how even that is named like a fact ("was requested"), which keeps it routable like any event.

The test at work: if the producer would be surprised that nobody reacted, it is a command. If it would not care, it is an event.

Producer, broker, consumer

The producer writes the message. The broker (RabbitMQ here) receives it on an exchange, which is a router with no storage, and copies it into every queue whose binding matches. The queue stores the message until a consumer takes it and acks it. If you know EventBridge: the exchange plays the event bus, a binding plays a rule with its pattern, and the queue plays the SQS target.

Why asynchronous between services here

Two rules in AGENTS.md section 4 force it:

  • Rule 2. Between api, agent and contact, only asynchronous messages through the outbox and RabbitMQ. Synchronous HTTP only at the edge.
  • Rule 3. A service that needs another's data keeps its own read model fed by events; the agent never calls api.

The reason is failure isolation. If agent called api over HTTP on every chat message, an api outage would take chat down too, and two services that cannot run without each other are a distributed monolith. With events, api can be down for an hour: agent keeps answering from its own copy, which is a little stale. That trade, availability for a few seconds of staleness, is called eventual consistency, and the pattern of copying the data a service needs into its own store is event-carried state transfer.

Section 2

The ping, end to end

system.ping.v1 exists only to prove the path works. api-worker sends one every 5 minutes (HEARTBEAT_INTERVAL_MS, default 300000), and in development POST /dev/ping sends one on demand and answers 202 with the event id. Its contract, in packages/contracts/src/events/system-ping.v1.ts:

export const systemPingV1 = defineEvent(
  "system.ping.v1",
  z.object({ trigger: z.enum(["manual", "heartbeat"]) }),
);

defineEvent gives it a routing key system.ping.v1 (the pattern <context>.<event>.v<N>), a CloudEvents type dev.jadero.system.ping.v1, and a Zod schema for the whole envelope.

  1. The outbox row, in the same transaction transactional outbox

    PingService.send opens a transaction with withTransaction and calls addToOutbox (packages/messaging/src/outbox/outbox.ts). Nothing talks to the broker here. For the ping the transaction holds only this row; in a real use case it holds the state change too, so the business row and the event commit together or not at all. That is the fix for the dual-write problem: "write the database, then publish" loses the event when the process dies between the two.

    INSERT INTO messaging.outbox (id, type, routing_key, envelope) VALUES ($1, $2, $3, $4)

    The table, from packages/messaging/src/schema.ts:

    ColumnHolds

    A partial index outbox_unsent on next_attempt_at WHERE published_at IS NULL keeps the poll cheap. The envelope stored in that row looks like this (the id and traceparent are examples):

    {
  "specversion": "1.0",
  "id": "019a0b7c-3f10-7a2e-9c41-5d2e8b6f0a13",
  "source": "jadero/api",
  "type": "dev.jadero.system.ping.v1",
  "time": "2026-10-19T09:00:00.000Z",

  "data": { "trigger": "heartbeat" }
}

    createEnvelope validates it against the contract before the insert, so a producer cannot write a row its consumers would reject. The traceparent is the trace of the request that wrote the row, so the trace continues across the broker.

  2. The relay claims and publishes message relay atomic claim

    OutboxRelay (packages/messaging/src/outbox/outbox-relay.ts) runs in api-worker, a second process type of api. It polls every 1 s, in one transaction:

    SELECT id, routing_key, envelope, attempts FROM messaging.outbox
 WHERE published_at IS NULL AND next_attempt_at <= now()
 ORDER BY created_at LIMIT 50 FOR UPDATE SKIP LOCKED

    FOR UPDATE locks the claimed rows; SKIP LOCKED makes a second relay skip them instead of waiting. For each row it restores the trace context from envelope.traceparent and calls MessageBus.publish, which resolves only when the broker sends a publisher confirm (timeout 5 s). Every confirmed id is then marked in the same transaction:

    UPDATE messaging.outbox SET published_at = now() WHERE id = ANY($1::uuid[])

    That published_at is what "sent" means. A crash after the confirm and before the commit leaves the row unmarked, so the next poll publishes it again. That is deliberate: at-least-once, and the consumer's inbox absorbs the duplicate. Published rows are deleted after 7 days by a daily cleanup.

  3. On the wire

    The RabbitMQ adapter publishes to exchange jadero.events with routing key system.ping.v1. The body is the envelope as JSON (CloudEvents structured mode). AMQP properties: contentType: application/cloudevents+json, persistent: true, messageId set to the envelope id.

  4. Exchange, binding, queue publish-subscribe

    jadero.events is a durable topic exchange. The queue agent.system.ping (named <service>.<purpose>) has one binding on it with key system.ping.v1, declared in packages/messaging/src/topology/jadero.ts:

    { name: "agent.system.ping", service: "agent", bindings: [systemPingV1.routingKey] }

    The key matches, so the broker stores a copy in that quorum queue, then confirms to the relay. A second service wanting pings would add its own queue and binding; the producer would not change.

  5. The consumer takes it

    HeartbeatConsumer (apps/agent/src/modules/heartbeat/heartbeat.consumer.ts) subscribes to agent.system.ping with the systemPingV1 contract. The adapter consumes with prefetch 4: at most four unacked deliveries at a time, because each holds one pooled database connection (pool max 6). Before the handler runs, the shared dispatch parses the body as a CloudEvents envelope, picks the subscription by type, and validates data with the contract.

  6. Inbox row and dedupe idempotent consumer

    One transaction holds the inbox insert and the effect:

    INSERT INTO messaging.inbox (consumer, event_id, type) VALUES ($1, $2, $3)
ON CONFLICT DO NOTHING RETURNING event_id
-- ('agent.system.ping', '019a0b7c-...', 'dev.jadero.system.ping.v1')

    The primary key is (consumer, event_id). If a row comes back, this is the first delivery and the heartbeat upsert runs. If nothing comes back, it is a duplicate: no effect, a debug log line, and the handler still returns done. If the effect throws, both roll back together, so a retry starts from scratch. Inbox rows are deleted after 30 days.

    The effect itself, in heartbeat.repository.ts, also defends against order:

    INSERT INTO heartbeat.broker_heartbeat (source, last_event_id, last_trigger, last_seen_at) ...
ON CONFLICT (source) DO UPDATE SET ...
WHERE broker_heartbeat.last_seen_at < excluded.last_seen_at

    A retried old ping that arrives after a newer one changes nothing. Dedupe handles "twice"; this guard handles "late".

  7. Ack

    The handler never acks itself; it returns an outcome (done, retry or dead), and the adapter turns it into a disposition with the pure function dispose in packages/messaging/src/outcome.ts. done means ack: the broker deletes the message from the queue.

Section 2, continued

Failure paths

The handler throws: retry through wait queues retry with backoff

A thrown error in the handler becomes retry. A bad payload (invalid envelope, unknown type, data that fails the contract) becomes dead at once, because retrying cannot fix it. For retry, the delay depends on the attempt number, carried in the header x-jadero-attempt:

DeliveryOutcome retry gives
attempt 1copy to agent.system.ping.retry.10s, header attempt 2
attempt 2copy to agent.system.ping.retry.1m, attempt 3
attempt 3copy to agent.system.ping.retry.10m, attempt 4
attempt 4dead-letter: "retries exhausted after 4 attempts"

The mechanism, step by step. The consumer does not nack. It publishes a copy, waits for its confirm, and only then acks the original:

  1. Copy to exchange agent.retry (direct, one per service) with routing key agent.system.ping.retry.10s. A direct exchange routes on exact key equality, so it lands in that wait queue only.
  2. The wait queue has no consumer. Its policy sets message-ttl: 10000, dead-letter-exchange: agent.retry and dead-letter-routing-key: agent.system.ping. The TTL is the timer.
  3. After 10 s the broker dead-letters the message to agent.retry with key agent.system.ping, and the binding agent.retry → agent.system.ping puts it back in the consumer queue.
flowchart LR
  Q["agent.system.ping"] -->|"deliver, attempt 1"| H["HeartbeatConsumer"]
  H -->|"throws, copy with attempt 2"| RX["agent.retry direct"]
  RX -->|"key agent.system.ping.retry.10s"| W["agent.system.ping.retry.10s, TTL 10 s"]
  W -->|"TTL expires, dead-letter"| RX
  RX -->|"key agent.system.ping"| Q
  H -.->|"ack original after copy confirmed"| Q

Why route the retry back through a per-service exchange instead of republishing to jadero.events? Because another service bound to the same event would get the retry too and run its handler twice for nothing. The retry goes to this queue only.

If the copy is not confirmed (broker trouble), the adapter holds the delivery 1 s and then nacks it with requeue. It never acks without its copy, so the message cannot vanish; and the pause stops a tight loop, because on RabbitMQ 4.3 a nack does not count toward the delivery limit.

Dead outcome or exhausted retries: the DLQ dead-letter queue

For dead, the adapter publishes a copy to agent.retry with key agent.system.ping.dlq, headers x-jadero-attempt and x-jadero-dead-reason (field names only, never values), then acks. The message rests in agent.system.ping.dlq. ADR-012 plans WP-50 to read DLQs into a dead_letters table with an admin replay action.

The consumer crashes mid-message: delivery limit 20 poison message

A message that kills the process (out of memory, a segfault in a native library) never reaches dispose. The channel closes with the delivery unacked, and the quorum queue redelivers it and counts the delivery. The consumer queue's policy sets delivery-limit: 20 with dead-letter-exchange: jadero.dlx and dead-letter-routing-key: agent.system.ping. On the 21st try the broker itself moves it through jadero.dlx (direct) to agent.system.ping.dlq. Without the limit, one poison message would crash-loop the consumer forever.

flowchart LR
  Q["agent.system.ping, delivery-limit 20"] -->|"deliver"| H["consumer crashes"]
  H -->|"unacked, redelivered, counted"| Q
  Q -->|"limit passed, broker dead-letters"| DLX["jadero.dlx direct"]
  DLX -->|"key agent.system.ping"| DLQ["agent.system.ping.dlq"]
  C["consumer returns dead"] -->|"copy, key agent.system.ping.dlq"| RX["agent.retry"]
  RX --> DLQ

Both dead-lettering paths are safe: the policies set dead-letter-strategy: at-least-once with overflow: reject-publish, because the quorum default is at-most-once, which could drop a message on its way to the DLQ.

An unroutable message: the alternate exchange alternate exchange

A producer publishes content.published.v1 before any queue binds it. Without protection, a topic exchange silently drops a message that matches no binding, and the publisher still gets its confirm. Here jadero.events is declared with alternate-exchange: jadero.unrouted, a fanout exchange bound to a quorum queue also named jadero.unrouted. The message is kept there to inspect. The retry exchanges have the same alternate exchange, so a copy whose wait queue is missing (tiers out of step with the topology) is kept too.

flowchart LR
  P["relay publishes content.published.v1"] --> X["jadero.events topic"]
  X -->|"no binding matches"| AE["jadero.unrouted fanout"]
  AE --> UQ["jadero.unrouted queue"]

The broker is down: the outbox holds store and forward

The request path never touches the broker, so POST /dev/ping still answers 202. The relay's publish times out after 5 s; the row gets attempts + 1, last_error set to the error kind, and next_attempt_at = now() + backoff, where backoff is 1 s doubling up to 60 s. The relay then ends the batch instead of waiting 5 s per row while holding row locks. Rows pile up in Postgres, which is durable, and drain in created_at order once the broker returns. On the consumer side, start() never blocks on the broker: consumers attach when it comes back.

Exchanges, queues, policies

Four exchange types

TypeRoutes byExampleIn this repo
directexact routing key equalitykey agent.system.ping.dlq reaches only the queue bound with that keyagent.retry, jadero.dlx
topicdot-separated words with wildcards: * one word, # zero or moresystem.ping.* matches system.ping.v1; content.# matches content.published.v1; *.published.* matches any context's publishjadero.events

The same matching rules are coded in packages/messaging/src/topic.ts (topicMatches) so the in-memory bus used in unit tests routes exactly like the broker. This repo binds one exact key per contract version rather than wildcards, so a v2 never reaches a consumer that only understands v1.

Three queue types

TypeWhat it isWins when
quorumreplicated with the Raft consensus algorithm, durable, tracks a delivery count per messagethe message must not be lost; the default for anything that matters
classicthe original single-node queuetemporary, non-critical queues (reply queues, caches)
streaman append-only log; consumers read from an offset and nothing is deleted on ackreplay, many readers of the same history, Kafka-like use

Every queue here is quorum. On a single node there is no replication to gain, but quorum queues bring the delivery limit that stops poison messages, and the topology stays the same if the broker ever gets more nodes.

Declared arguments versus policies

A queue's arguments are fixed when it is declared: RabbitMQ refuses to change them later, so changing a TTL would mean deleting the queue and its messages. A policy is a rule matched by name pattern that the broker applies, and re-applies at once when it changes. So buildDefinitions (packages/messaging/src/topology/definitions.ts) declares only x-queue-type: quorum, and everything tunable is a policy:

// policy "agent.system.ping", pattern ^agent\.system\.ping$
{ "dead-letter-strategy": "at-least-once", "overflow": "reject-publish",
  "dead-letter-exchange": "jadero.dlx", "dead-letter-routing-key": "agent.system.ping",
  "delivery-limit": 20 }
// policy "agent.system.ping.retry.1m"
{ ..., "message-ttl": 60000, "dead-letter-exchange": "agent.retry",
  "dead-letter-routing-key": "agent.system.ping" }

Topology as code, and no configure right least privilege

The topology lives in one place, packages/messaging/src/topology/. pnpm --filter @jadero/messaging topology runs scripts/write-definitions.mjs, which writes infra/rabbitmq/definitions.json (dev, with fixed dev passwords), infra/rabbitmq/server/definitions/prod.json and staging.json (no users), and infra/rabbitmq/server/permissions.tsv, which provision-users.sh applies with passwords from the environment. A test fails while the generated files are stale.

The adapter declares nothing. Service users get configure: ^$, so they cannot create, change or delete an exchange or queue. A buggy deploy cannot quietly redefine the topology; only the reviewed definitions can. The rights, from buildPermissions:

One virtual host per environment

A vhost is a namespace inside one broker: its own exchanges, queues and permissions. Dev uses dev; the server's one RabbitMQ serves /prod and /staging. User names are global, so they carry the environment (agent_staging), and a staging user has no rights on /prod. It is the same idea as one AWS account per environment, at a fraction of the cost.

Section 4

Delivery semantics

GuaranteeHow you get itWhat breaks
at-most-onceack before processing, or fire and forgeta crash loses the message
at-least-onceack after processing; publish again until confirmedduplicates: a crash between work and ack redelivers
effectively-onceat-least-once plus an idempotent consumeronly effects outside the transaction (an email, an external API call)

True exactly-once delivery across a network is not available: the sender can never tell "lost" from "slow". What you can build is exactly-once effect. This repo has duplicates at two points by design: the relay's crash window between confirm and commit, and the consumer's crash window between commit and ack. The inbox covers both, because the dedupe row commits in the same transaction as the effect.

The inbox only protects effects inside the consumer's own database transaction. If a handler sends an email, a duplicate sends a second email. The fix there is an idempotency key sent to the provider, or recording "sent" before sending and accepting a rare miss: you choose which failure you prefer.

Ordering

A single queue with a single consumer and prefetch 1 delivers in order. Every one of these breaks it: prefetch above 1 with async handlers, two or more consumers, a retry (the message comes back 10 s later behind newer ones), and the relay itself if several relays ran. So design consumers to not need order: carry a timestamp or version and ignore older ones, which is exactly the heartbeat's WHERE last_seen_at < excluded.last_seen_at guard. When order truly matters per entity, partition by key (Kafka partitions, SQS FIFO message groups, RabbitMQ single active consumer or a consistent hash exchange).

Poison messages

A message that can never succeed. Three guards here: validation in dispatch sends bad payloads to the DLQ at once, the retry tiers cap a throwing handler at four attempts, and the delivery limit catches messages that crash the process.

Prefetch and backpressure backpressure

Prefetch is how many unacked messages the broker pushes to one consumer before waiting. Too high: one slow pod hoards messages others could take, and memory grows. Too low: the consumer idles between round trips. Here it is sized from a downstream limit: prefetch 4 against a pool of 6 connections, so a burst of pings waits in the queue, which is durable and cheap, instead of failing on an exhausted pool. That is backpressure: the slow part sets the pace and the queue absorbs the rest. ADR-029 sets 10 as the default in the adapter.

Competing consumers competing consumers

Three replicas of a Kubernetes Deployment consume the same queue. Each message goes to exactly one pod. This scales throughput, and a dead pod's unacked messages go back to the others. The cost: order across messages is gone, since pod 2 may finish message 7 before pod 1 finishes message 6. Each pod's prefetch caps its share. HPA on queue depth (with KEDA, for example) adds pods when the queue grows.

Fan-out publish-subscribe

A supplier.updated.v1 event feeds search indexing, notifications and an external integration sync. Each consuming service binds its own queue, so each gets every event, at its own pace, with its own retries and DLQ. The notification service being down does not delay search. Adding a fourth consumer is a binding, not a producer change. This is the shape jadero.events is built for.

Both combine: each fan-out queue can have competing pods. The rule: one queue per consumer purpose (ADR-029), as many pods per queue as throughput needs.

Worked case: a risk alert sync every minute

A procurement product integrates an external supplier risk alert provider. Every minute, for every organization with the integration on, it pulls new alerts and stores them. There are 400 organizations; the provider allows batches of 20 organizations per call, so 20 calls a minute. A call takes 1 to 5 s, sometimes 30 s when the provider is slow.

(a) A CronJob with a database lock

A Kubernetes CronJob, schedule * * * * *, concurrencyPolicy: Forbid so a new run is skipped while the previous Job still runs. The Job loops over batches of 20.

Forbid is per CronJob and Kubernetes documents schedules as roughly once, so two runs are rare but possible. Guard it in the database: pg_try_advisory_lock(key) at start (a second run gets false and exits), or per-organization claims, SELECT ... FROM org_sync WHERE next_sync_at <= now() LIMIT 20 FOR UPDATE SKIP LOCKED, then set next_sync_at = now() + 1 minute. In a long-running Deployment instead of a Job, the same advisory lock is leader election; this repo's ADR-012 plans exactly that if a cron process is ever scaled out.

Guarantees: one runner at a time; simple to reason about. Fails by: one slow call delays every batch behind it; with Forbid, a run longer than a minute skips the next minute; throughput is one process.

(b) A scheduler and a work queue

A tiny scheduler (one CronJob or a leader-elected loop) publishes one work message per batch, risk.sync.batch.requested.v1 with the 20 organization ids and the minute it covers, into a work queue. N pods consume it as competing consumers.

Guarantees: batches run in parallel; a slow batch blocks only its pod; each batch gets retries and a DLQ for free. Fails by: if processing falls behind, minutes pile up, so the scheduler must not enqueue a batch whose previous one is still pending (keep the per-org next_sync_at claim, or dedupe on batch id plus minute in an inbox); N pods together can break the provider's rate limit, so you need a shared limiter; duplicates must be harmless (upsert alerts by the provider's alert id).

When each wins. At 20 calls a minute that usually finish in seconds, (a) wins: one moving part, nothing to deduplicate, and the claim table already gives you per-org scheduling. Move to (b) when one run no longer fits in the interval, when you need per-batch retry and dead-lettering visible to operations, or when each batch is expensive enough that losing one pod should not stall the rest. A common middle step: keep the claim table and run the claim loop in several pods, since SKIP LOCKED already makes them competing consumers on Postgres, with no broker.

Peculiarities to remember

  • RabbitMQ pushes to consumers and forgets on ack. Rich routing in the broker; history is gone unless you use streams. An unroutable message is dropped unless you add an alternate exchange or mandatory publishing.
  • EventBridge + SNS + SQS is managed and pay-per-use, all at-least-once. Routing on payload fields is its strength. Every hop has its own retry and DLQ settings, so a failure can hide at the rule target, the SNS subscription or the SQS queue: check all three. The routing table you know at work (an event store forwarding to SNS topics) is the same exchange-binding-queue idea built from three services.
  • Kafka is a log, not a queue: consumers track an offset, many groups read the same history independently, and replay is free. Parallelism is capped by partition count, and one slow message blocks its partition, which is why retry topics exist.
  • NATS JetStream is small and fast, with subjects as a light routing model and both queue-like and log-like retention. Fewer built-in failure topologies than RabbitMQ; ADR-029 rejected it here because Nest's built-in NATS transport is fire and forget and the learning transfers less.

Section 7

Event sourcing and CQRS

Event sourcing stores every change as an immutable event and treats them as the source of truth. Current state is not stored; it is derived by folding the events in order. CQRS (command query responsibility segregation) splits the write model from read models: writes append events, and projections turn them into tables shaped for each query.

Worked example: a supplier rating

A supplier's rating comes from assessments. Instead of a supplier_rating row with a score that gets overwritten, store the stream for supplier S-17:

seq  type                              at          data
1    rating.assessment.recorded.v1     2026-03-02  { criterion: "delivery", score: 4 }
2    rating.assessment.recorded.v1     2026-03-02  { criterion: "quality",  score: 3 }
3    rating.weights.changed.v1         2026-05-10  { delivery: 0.6, quality: 0.4 }
4    rating.assessment.recorded.v1     2026-07-21  { criterion: "quality",  score: 5 }

The fold is a pure function, state = events.reduce(apply, empty), with equal weights by default:

After eventdeliveryqualityweightsrating
2430.5 / 0.53.5
3430.6 / 0.43.6
4450.6 / 0.44.4

"What was S-17's rating on 2026-06-30?" Fold only the events with at <= 2026-06-30: 3.6. A table that stores only the final 4.4 cannot answer that, and an auditor asking why a supplier was blocked in June needs exactly that answer. That is the real reason to choose event sourcing: the history is the product.

  • Projections. A consumer folds events into supplier_rating_current for the list page, another into supplier_rating_monthly for a chart. Both can be dropped and rebuilt from the stream.
  • Snapshots. A supplier with 30,000 events is slow to fold, so store the state every N events (say at seq 1000) and fold only what came after.
  • Upcasting. Events are never edited. When v2 changes scores from 1 to 5 into 0 to 100, an upcaster converts v1 to v2 in memory while reading (score * 20), so the fold only knows the newest shape.
  • The cost. Every read model is eventually consistent; schema changes need upcasters forever; a wrong event cannot be deleted, only compensated by a new one; deleting personal data needs crypto-shredding or stream rewriting; and the team must think in events. For most CRUD it is a large tax for history nobody asks for.

The outbox is not event sourcing

Transactional outbox (this repo)

State lives in normal tables and is the source of truth. The outbox row is a delivery buffer: it exists to get a message to the broker, and published rows are deleted after 7 days. Losing the outbox history loses nothing important.

Event sourcing

The event store is the state. Nothing is ever deleted; tables are disposable projections. Losing the events loses the business.

They combine well: an event-sourced service still needs a reliable way to publish, and its event store often doubles as the outbox.

How it could apply here, and what the repo does instead

  • The agent's usage and budget ledger (ADR-021, planned): every model response priced and summed into usage.llm_usage, with a daily cap. Append-only usage rows already look like events; full event sourcing would add projections of spend per day for a cap that resets daily. Overkill: the plan sums rows.
  • Content revisions (WP-12): each localized type has a *_revisions table of immutable jsonb documents, and a *_translations row with pointers to the latest and the published revision. That keeps full history and can show any past version, but each revision is a full snapshot, not a delta event, and the pointers are mutable state. It is versioned snapshots, the cheaper cousin of event sourcing.
  • The agent's search index (D-42): a CQRS read model in the sense that matters, derived from api's content and rebuildable from events. CQRS without event sourcing is common and cheap; this is that.

Section 8

Choreography and orchestration

A business process that spans services cannot use one database transaction. A saga is the sequence of local transactions, each with a compensating action that undoes it if a later step fails.

Choreography choreography

No coordinator. Each service reacts to events and emits its own. content.published.v1 makes agent reindex and api-worker rebuild the PDF; neither knows about the other. Wins with few steps and independent reactions, which is this repo. Loses when the flow grows: nobody can see the whole process, and cycles creep in.

Orchestration orchestrated saga

One orchestrator holds the state of the process and sends commands: "verify certificate", then "update supplier status", then "notify", compensating on failure. Wins with many ordered steps, timeouts, human approvals and the need to answer "where is request 812 stuck?". Tools: a state table with a process manager, or a workflow engine (Step Functions, Temporal).

A configurable approval flow, where a change passes steps with conditions and assigned reviewers, is orchestration by nature: the order and the waiting are the business.

Self-check

Eight questions

Each carries what you need. Answer before opening.

1. The relay publishes row R, the broker confirms, and the worker is killed before COMMIT. What happens to R, and who absorbs the effect?

The claim's transaction rolls back, so published_at stays null and the row lock is released. The next poll claims R and publishes it again: the consumer receives the same envelope id twice. The inbox's (consumer, event_id) primary key turns the second delivery into a no-op. At-least-once publishing plus an idempotent consumer.

2. A handler throws on every attempt. How many times does it run, and over roughly how long, before the message stops?

Four runs: the first, then after 10 s, 1 min and 10 min. After the fourth throw, dispose finds no tier left and dead-letters it to agent.system.ping.dlq with "retries exhausted after 4 attempts". About 11 minutes plus processing time.

3. Why does a retry go through agent.retry with an exact key, instead of being republished to jadero.events?

Publishing to the topic exchange would route the copy to every queue bound to that event, so other services would run their handlers again. The per-service direct exchange and the wait queue's dead-letter routing key send it back to the one queue whose handler failed.

4. You need the retry delay changed from 1 min to 2 min in production. What do you change, and why does nobody need to delete a queue?

The tier in DEFAULT_RETRY_TIERS_MS, then regenerate the definitions. The delay is a policy (message-ttl), not a declared argument, and the broker applies a changed policy at once. Note the wait queue's name contains the delay label (.retry.2m), so a new tier means a new wait queue; the alternate exchange on agent.retry keeps any copy sent while the adapter and topology are out of step.

5. A consumer process dies with an out-of-memory error on one specific message, every time. What stops the crash loop?

The handler never returns, so the retry tiers never apply. The quorum queue counts each redelivery; the policy's delivery-limit: 20 makes the broker dead-letter the message through jadero.dlx to agent.system.ping.dlq, and the pod recovers.

6. An online shop: an order-paid event must update stock, send a receipt email, and notify the warehouse. One service, one queue, or one queue per reaction?

One queue per reaction (fan-out). Each has its own failure: the email provider down must not block stock or the warehouse, and each needs its own retries and DLQ. Stock can be idempotent with an inbox; the email needs an idempotency key with the provider, because it is an effect outside the database.

7. You scale the agent consumer to three pods. The heartbeat table still ends up right. Why, even though order is lost?

The upsert only writes when the stored last_seen_at is older than the incoming one. Whatever order the three pods finish in, the newest ping wins. Commutative, last-writer-wins updates make ordering irrelevant for this effect.

8. A booking platform wants to show what a hotel's cancellation policy was on the day a guest booked. Is the outbox enough, and what is the cheapest design that works?

No: outbox rows are deleted after delivery and are not the source of truth. Full event sourcing would work but is costly. The cheapest fit is versioned snapshots, like this repo's content revisions: keep every policy version with its validity time, and store the version id on the booking.
