# The data layer: migrations per service, transactions owned by the use case

WP-5 got two services talking with hand-written SQL for the outbox and the inbox. WP-10 replaces that with a real data layer: Drizzle, generated migrations per service, and a clear rule for who opens a transaction. I use an ORM and migrations every day, and still the gaps were in places I thought I knew. <!-- owner: check -->

## What I built

A shared `DatabaseModule` in `platform-nest`: a lazy Postgres pool, Drizzle on top, a readiness check with its own 1 second budget and a clean shutdown after the HTTP server.

Migrations generated by drizzle-kit from schema files, reviewed as SQL in the PR, and applied by each service in a one-off `db:migrate` step, never at boot. The outbox and inbox tables are defined once in `@jadero/messaging/schema`, and each service generates only the tables it uses into its own database.

`withTransaction` for layered modules and a unit of work port for hexagonal ones. The use case owns the transaction, and the outbox or inbox row is written on the same connection as the business change.

Integration tests on real Postgres with Testcontainers, connected as an ordinary role with no superuser rights, so a migration that needs a superuser fails in the PR instead of during a deploy. Two guards in `pnpm verify` catch schema drift and edits to migrations `main` already has.

## What I learned

**I swapped liveness and readiness.** Asked what happens when Postgres is down at boot, I had `/health/live` failing and `/health/ready` fine. It is the other way round. Liveness checks nothing, so nobody restarts the process for a database outage. Readiness answers 503 until Postgres is back, and the lazy pool recovers with no restart. The TypeORM setup I know connects eagerly at boot, which explains my instinct. <!-- owner: check -->

**An edited migration is skipped silently.** I thought editing an applied migration might fail. It does not. Drizzle only applies entries newer than the last one it recorded and never compares hashes, so old databases never get the change and new ones do. Tests pass while production differs. That gap became the `check:migrations` guard.

**The inbox and its effect must commit together.** I thought the inbox row would stay when the second write failed. Both writes share one transaction, so both roll back and the redelivery gets processed normally. If the inbox committed on its own, the retry would be dropped as a duplicate and the effect lost for good. Idempotency without atomicity loses messages.

**Fakes need contract suites.** I pushed back on fakes because they drift from Postgres. The answer is the split: business rules are tested on fakes, storage behavior lives in a contract suite that runs against both the fake and Postgres. I also had the wrong reason for ports: not swapping the database someday, but fast and honest tests of the rules.

**There is no transaction across services.** In the explain-back I said that extracting `knowledge` into its own service means adding its table to the port so it shares the transaction. That is backwards. Two databases cannot share a transaction. Calls become events through the outbox, or a read model fed by events, and a use case that writes both sides splits into a local commit plus an event. This is the gap that matters most, and it goes to my study list for R1. <!-- owner: check -->

I also missed that the relay has its own transaction, so a ping is three transactions, not two.

## What I would change

The explainer contradicted itself on whether layered modules get ports, and the first build gave ports to ping and heartbeat before anyone noticed. Next time I want the explainer checked against itself before the first step. <!-- owner: check -->

A few check questions were asked in code names I never see, and one gave away its own answer. I want questions about flows and failures, explained first. <!-- owner: check -->

The test database helper now exists in four copies. I should have pulled it into one place on the second copy, not the fourth. <!-- owner: check -->
