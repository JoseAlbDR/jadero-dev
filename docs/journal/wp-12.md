# The content domain: revisions, a published pointer and a read side that cannot write

WP-12 is the first real business module in this repo: every piece of site content now has a model, a history and a public API the pages in WP-16 can read. Most of what I learned came from the questions I got partly wrong. <!-- owner: check -->

## What I built

A hexagonal `content` module in `api`. Each content item is one aggregate with its translations and revisions. A revision is a frozen `jsonb` document, every save appends one, and publishing moves a per-locale pointer. Knowledge entries go live through an approval bound to one revision.

Persistence sits on WP-10's data layer: a version column per aggregate, compare-and-set first in every save, and contract suites that run on the fakes and on Postgres.

The read side is separate. Public reads run their own SQL from the published pointers, on a second pool that logs in as `content_reader`, a role with `SELECT` on the public tables only, never the private provenance table. The routes are versioned (`/v1/content/...`), cached with `stale-while-revalidate` and fall back to English per item when German is missing.

`platform-nest` also got hardened for every service: security headers, a body limit, `no-store` on errors, and error logs and bodies that never echo request data.

## What I learned

**A lazy pool hides a wrong password.** Asked what a wrong reader password does after a deploy, I missed that before this WP nothing would have failed. The pool connects lazily and readiness checked only the main pool, so the app said ready and every public page answered 500. Readiness is only as good as what it checks.

**I swapped liveness and readiness again.** Same mistake as WP-10, in the explain-back. Live stays 200 because a restart cannot fix a password, ready goes 503. Twice is a pattern, so it stays on my study list. <!-- owner: check -->

**Optimistic concurrency is an integer, and it is about what the caller saw.** I had the idea but not the mechanism: `UPDATE ... WHERE version = expected`, and zero rows means a conflict. Not a timestamp, because two saves can share a millisecond. A stale version is refused even if nobody else wrote: the server cannot tell "me, earlier" from "another tab".

**The dual write.** I said a central outbox service over HTTP is bad because of coupling. The real problem is that the commit and the call cannot share a transaction, so you lose events or announce things that never happened.

**Stale-while-revalidate serves the old copy first.** Inside the stale window the visitor gets the cached copy at once and the refresh runs in the background. And the ETag is a hash of the built body, so a 304 saves bandwidth, not the query.

**A unique index makes the second insert wait.** I thought two concurrent seeds would each keep their own profile. The unique index on a constant makes the second insert wait on the first's uncommitted row, then `ON CONFLICT DO NOTHING` turns it into a normal conflict.

**A grant covers whole tables.** I said an injection on the reader connection reads everything. It reads only the granted tables, never the provenance or the outbox, and cannot write. But it does read drafts, because the grant covers the whole revisions table.

## What I would change

The explain-back questions were tied to this project's code. I want questions that transfer to my job and other projects, and I proposed that as a process change.

Two hardening gaps (the request logger mounted after the body parser, and parser errors echoing input) only showed up in the last step. I would write those request-level tests the first time `platform-nest` is touched, not at the end. <!-- owner: check -->

Splitting step 5 so I reviewed the SQL before any repository was built on it worked well, and I want that for every new schema. <!-- owner: check -->
